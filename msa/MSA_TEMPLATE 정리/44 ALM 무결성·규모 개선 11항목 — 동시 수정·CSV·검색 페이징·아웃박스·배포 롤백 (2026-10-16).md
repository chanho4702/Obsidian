## 1. 무엇을 고쳤나

### 백엔드
- **동시 수정 409**: 잠금을 잡은 뒤 `em.refresh`로 최신 version을 다시 읽어, 낡은 version으로 들어온 수정은 409를 낸다(전에는 잠금 전에 읽은 값끼리 비교해 덮어쓰기가 통과).
- **CSV 가져오기 행별 트랜잭션**: 행마다 `REQUIRES_NEW`, 바깥 트랜잭션은 없다. 한 행이 실패해도 앞선 행은 남고 실패 행만 보고된다.
- **보드 이동 알림**: 보드에서 상태를 옮겨도 이슈 수정과 같은 알림이 나간다.
- **이벤트 아웃박스(V26)**: `event_outbox` + `event_outbox_lock`. 커밋 후 본문 없는 이벤트라는 확정 결정은 그대로이고, 발행 유실만 막는다. 발행 워커는 잠금 행(`skip locked`)으로 한 곳만 돌아 여러 인스턴스에서도 id 순서를 지킨다(Codex 지적 반영).
- **첨부 413**: 한도를 넘으면 오류 계약(`{"error": ...}`)대로 413을 돌려준다.
- **검색**: 상태 분류·`openOnly`·마감일·`updatedSince`·정렬 필터, `/issues/aggregate` 집계 API, `/projects/{id}/labels`. 일괄 DTO 로딩으로 **SQL 문 수가 크기 5에서 12→4, 크기 50에서 102→4**.

## 3. 덤으로 찾은 기존 결함 — Postgres에서만 터지는 since 필터

origin/main을 Postgres로 돌리면 13건이 실패했다. 12건은 **감사 로그·변경 이력의 `(:since is null or x >= :since)`**. PostgreSQL JDBC가 시각 null을 타입 미지정으로 보내서 `could not determine data type of parameter $8`로 500이 난다. H2는 통과해서 지금까지 가려져 있었다. 운영(Postgres)에서는 since 없이 감사 로그·스프린트 리포트를 열면 실제로 실패하는 결함이다.

→ `x >= coalesce(:since, x)`로 바꿔 컬럼 타입에서 추론하게 했다(`87257fc`). Postgres 12→0, H2 267/267. 피처 브랜치와 충돌 없이 합쳐진다.

나머지 1건(`AlmContentGrpcServiceTest`)은 결함이 아니다. `@DataJpaTest`가 내장 H2로 바꿔 끼우는데, 내가 환경변수로 Flyway를 켜서 Postgres용 V1이 H2에 돌아간 것이다.
