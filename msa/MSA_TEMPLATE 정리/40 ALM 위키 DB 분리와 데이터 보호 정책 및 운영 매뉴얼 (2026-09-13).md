# 40 — ALM·위키 DB 분리와 데이터 보호 정책·운영 매뉴얼

이전 진단: [[39 플랫폼 전체 진단과 온프레미스 제품화 결과 (2026-09-13)]]

## 먼저, 쉽게 설명하면

현재 ALM과 위키는 **서랍은 다르지만 같은 장롱 안에 있는 상태**다.
`almdb`와 `wikidb`는 이미 구분돼 있지만 PostgreSQL 서버와 디스크·관리 계정을 공유한다.
따라서 장기 방향은 ALM용 DB 서버, 위키용 DB 서버, 공통 서비스용 DB 서버를 나누는 것이다.
다만 같은 컴퓨터 안에서만 나누면 컴퓨터 고장은 함께 맞으므로, 장애 대비에는 다른 호스트와 외부 백업이 필요하다.

백업도 DB 파일 하나를 복사하는 것으로 끝나지 않는다. 문서·이슈 DB, 첨부파일, 공동편집 상태,
로그인/암호화 키, 정확한 설치 버전이 함께 있어야 새 서버에서 서비스를 다시 열 수 있다.

**정책·도구·매뉴얼 준비와 검증은 끝냈다. 고객 데이터의 외부 정기 백업 체계가 이미 가동 중이라는 뜻은 아니다.**

쉽게 말하면 **복구 방법과 도구를 만들고 시험한 상태**다. 실제 고객 데이터의 외부 사본을 만들고
다른 서버에서 서비스 전체를 살리는 운영 인수는 외부 저장소·키·일정이 준비된 뒤 해야 한다.

## 1. 이번 요청의 결정

| 항목 | 결정 |
|---|---|
| 지금 DB 이동 | 하지 않음. 기존 데이터와 실행 중 서버 유지 |
| 목표 DB 구조 | PostgreSQL 유지, ALM / 위키 / 공통을 독립 인스턴스로 분리 |
| 공동편집 | 위키 DB와 함께 이동. Yjs 바이너리 원본 보존 |
| 기본 보관 | 일간 35개, 주간 12개, 월간 12개 + 변경 전/마지막 정상 복원본 별도 보호 |
| 삭제 | 외부 사본·복원 검증 전 자동 정리 금지. 기존 ALM 도구도 기본 자동 삭제 해제 |
| 서버 유실 | 다른 호스트에서 DB·파일·키·설치 자재를 복원한 뒤 업무 기능까지 확인 |
| 기본 손실/복구 목표 | RPO 24시간 / RTO 8시간. 실제 시험 전 보장값이나 SLA로 판매하지 않음 |
| 더 짧은 손실 시간 | WAL 기반 시점 복구와 객체 시점 정합성 구현이 선행. 현재 완료 아님 |
| 커밋/푸시 | 검증한 작업 브랜치만. main/master 병합·운영 자동 배포는 하지 않음 |

보관 숫자는 운영 기본안이다. 고객 계약·데이터 종류에 따른 법정 보관 기간을 확정했다는 뜻은 아니다.

## 2. 작성한 매뉴얼

저장소의 `infra/runbooks/`에는 재사용 가능한 운영 매뉴얼을, 작업 결과 기록은 이 보관함에만 둔다.

| 문서 | 쉬운 용도 |
|---|---|
| `index.md` | 무엇부터 읽을지와 설치 인수 기록 |
| `data-protection-policy.md` | 무엇을 얼마나 보관하고, 어떻게 삭제를 통제할지 |
| `backup-restore.md` | 사전 점검·백업·외부 사본·복원 연습 순서 |
| `disaster-recovery.md` | 서버 고장·삭제·손상·랜섬웨어 때 할 일과 금지 행동 |
| `installation-cases.md` | 개발/데모·단일 서버·분리 DB·폐쇄망·HA의 5개 설치 유형 |
| `database-separation.md` | ALM과 위키를 나중에 옮길 때의 준비·중단·검증·전환·복귀 제한 |

`INSTALL.md`와 `infra/README.md`도 연결했다. 기존의 운영 DB 선삭제 복원 예시와 설정 수정용 볼륨 초기화 안내를 제거했다.
메일/검색 선택 모드 및 필수 배포 env에 관한 오래된 설명도 실제 동작에 맞게 수정했다.
독립 문서 재검토에서 다른 절에 남아 있던 볼륨 삭제 안내도 제거했다. 신규 서비스의 누락 DB만 생성하는 절차,
대화형 비밀번호 변경, Google 공개 주소 설정, 복원 보조 이미지 사전 반입 조건을 보완했다.

## 3. 운영자가 특히 알아둘 점

- 현재 확인한 기본 PostgreSQL의 업무 DB는 **Keycloak을 포함해 9개**다. 사용자 정의 객체가 있는 관리 DB는 추가 보호해야 한다.
- 같은 서버의 `C:\backup`만으로는 서버 유실에 대비할 수 없다. 외부 암호화 사본과 별도 복호 키 보관이 필요하다.
- 점검한 로컬 백업 경로와 예약 작업에서 보호 체계의 증거를 찾지 못했다. 이것으로 모든 외부 저장소까지 조사했다거나 과거 백업이 한 번도 없었다고 단정하지 않는다.
- `member-avatars` 버킷 부재를 확인했다. 검사를 통과시키려고 빈 버킷을 만드는 것이 아니라 실제 원본 위치와 사용 여부를 확인해야 한다.
- Redis에는 검색 외 업무 상태도 있다. 전부 캐시로 취급해 삭제하지 않는다. 이관 업로드나 과거 메일 볼륨도 실제 데이터가 있으면 포함한다.
- ALM 휴지통 자동 정리 기본 60일과 위키 이력 정리는 백업 보존과 별개다. 보호 체계가 검증되기 전 정리 중지를 권고했지만, 이번에 앱 운영 설정을 바꾼 것은 아니다.
- 신규 도구는 현재 공유 DB 배치를 기준으로 한다. 미래 독립 DB·고객 외부 S3까지 자동 보호한다고 간주하지 않는다.

## 5. 백업 도구 교차검토 핵심

필수 자산이 빠졌는데도 성공하거나, 잘못된 경로·권한으로 민감 데이터가 새는 것을 우선 점검했다.

1. 온라인 비일관 백업 우회 제거, 모든 쓰기 주체·외부 DB 세션 확인.
2. 키·설정 누락 방지, 비밀뿐 아니라 전체 staging의 SID 기반 접근 제한.
3. 상위 junction·경로 겹침·manifest 변조/빈 목록/중복/추가 파일 거부.
4. 복원 대상 DB가 실제 존재하고 최소 하나인지 검증, globals SQL 무검토 실행 제거.
5. 로컬 검사와 외부 보호를 구분, 미래 시각·오래된 사본·불완전 복원 기록 거부.
6. 독립 DB 템플릿의 공유 DB 의존, URI 특수문자, 초기 관리자와 앱 권한 구분.

추가 격리 시험에서는 앱 계정과 초기 관리자 이름을 같게 지정하면 실패한 SQL에 시험용 비밀번호가 포함돼
PostgreSQL 서버 로그에 남는 것을 재현했다. 실제 비밀번호는 사용하지 않았고 자기 소유 시험 자원만 정리했다.
명령 인수에서 비밀번호를 빼는 것과 서버 오류 로그에 남지 않게 하는 것은 별개의 검증 항목으로 추가했다.

최종 초기화 스크립트는 동일 관리자·예약 이름·기존 역할을 비밀번호 SQL 전에 거부하고,
비밀번호를 argv에 넣지 않으며 해당 초기화 세션의 문장 로깅을 제한한다.
수정 중 `psql -c`의 변수 치환 불가로 정상 초기화가 실패하는 회귀도 발견했다(최초 6 실패/9 통과).
stdin 입력으로 보완한 뒤 **Codex가 직접 재실행한 실 DB 시험은 15개 모두 통과**했다.
정상 권한·접속과 서버 문장 로깅을 켠 정상/동일 관리자/예약 역할 경로의 시험 비밀번호 미노출을 확인했다.
이는 제공된 PostgreSQL 16 이미지 구성의 검증이며 고객의 추가 감사 확장·로깅 설정까지 포괄하는 보장은 아니다.

공통 검사도 대소문자 구분, 단일 컨테이너 ID, 모든 복제본의 키·마운트,
Windows 장치 경로 우회, 빈 객체 파일, dotenv 빈 값 덮어쓰기를 보완했다.
독립 재검사에서 남았던 두 번째 복제본의 잘못된 마운트도 최종 코드에서 거부되는 것을 확인했다.

이 검토 때문에 도구의 최종 확정이 문서 작성보다 늦어졌다. 운영 데이터에 실행해 보고 문제를 찾는 방식은 사용하지 않는다.

## 6. 아직 실제 설치별로 남는 일

외부 백업 저장소 주소·접근 방식은 제공되지 않았다. 암호나 키를 채팅으로 보내지 말고 안전한 비밀 관리 경로로 연결해야 한다.
저장소와 키가 준비되면 유지보수 수집 → 외부 전송 → 실패 알림 → 전체 복원 시험 → 일정 활성화의 인수 절차가 필요하다.
지금의 DB를 옮기지 않는다는 요청에 따라 실제 ALM/위키 분리 이관도 하지 않았다.

폐쇄망은 이미지·프론트 dist·인증서·테마·도구를 모두 반입해 인터넷 없이 시험해야 한다.
HA는 앱을 두 개 띄우는 것으로 끝나지 않고 DB·파일·인증·장애 전환까지 별도 인수가 필요하다.

### 실제 운영에서 해결할 우선순위

| 우선순위 | 남은 위험 | 완료로 인정할 증거 |
|---|---|---|
| P0 — 서버 유실 대비 | 외부 사본·복호 키·복원 가능한 설치 자재 미입증 | 다른 호스트에서 실제 외부 사본으로 전체 서비스 복원 |
| P0 — 누락 방지 | 아바타 등 원본 위치와 키/설정 일치 확인 필요 | 실제 저장소 목록과 수집 범위 대조, 기존 파일·암호문 복구 시험 |
| P1 — 지속 운영 | 예약 수집·외부 전송·실패 경보·보존 삭제 통제 미가동 | 성공/실패를 모두 시험한 운영 일정과 담당자 인수 기록 |
| P1 — 장애 영향 축소 | ALM·위키·공통 DB가 같은 호스트·관리 계정을 공유 | 계획된 분리 이관 및 앱/권한/백업 인수 시험 |
| P2 — 납품 옵션 | Linux·폐쇄망·HA 설치의 고객 환경 시험 필요 | 해당 설치 유형의 실호스트/망 차단/장애 전환 인수 결과 |

이 표는 도구 코드의 미해결 결함과 구분되는 **현장 적용 과제**다. 문서 작성이나 Git 푸시로 자동 완료되지 않는다.

## 7. 아키텍처와 온프레미스에 대한 결론

서비스와 업무 DB를 나누는 방향은 유지할 만하다. 당장 전체 구조를 다시 만드는 것보다,
**데이터를 잃지 않는 운영 체계 → 서비스별 DB 계정과 인스턴스 분리 → 고객 설치별 검증** 순서가 우선이다.
위키와 공동편집은 같은 데이터 소유 경계를 유지하고, 인증·조직 같은 공통 기반의 의존은 명시적으로 관리한다.

현재 기본 Compose는 개발·내부 검증에 사용할 수 있는 출발점이지, 그대로 모든 고객에게 납품할 운영 패키지는 아니다.
단일 서버 납품은 HTTPS·운영 인증 설정·실제 객체 저장소·외부 복원 시험을 갖춘 조건부 설치로 접근한다.
폐쇄망·Linux·HA는 설치 자재와 복구 도구까지 포함한 별도 인수 유형으로 관리해야 한다.
HA나 복제도 실수 삭제·랜섬웨어를 막는 백업의 대체가 아니다.

### 검토 출처와 제한

실제 Claude Fable가 구현하고 Codex가 독립 검토·재현·재검증했다. 별도 문서 리뷰와 공통 함수 리뷰도 반영했다.
첫 구조화 구현 작업 뒤 일부 보완은 Claude 일반 이어하기 턴에서 진행됐으며 이를 전부 정식 dispatch 완료로 소급 표기하지 않는다.
동결 후 새 최종 리뷰 세션을 연결하려던 시도는 프롬프트 전달 단계에서 실패해 승인 증거로 사용하지 않았다.
그 실패 세션만 정리했고 기존 Claude 터미널은 보존했다. **최종 승인은 주 Codex의 직접 검증 결과에 근거한다.**

### 아직 하지 않은 것

실제 운영 Execute·서비스 중단·DB 이관·외부 저장소 연결·백업 암호화 설정·일정/알림 활성화·다른 호스트 전체 복구는 하지 않았다.
외부 저장소와 안전한 키 전달 경로가 정해져야 현장 적용을 이어갈 수 있다.
현재 수집 도구는 S3 전체 버전/정책/메타데이터, Loki/메일 과거 로그, Grafana UI 생성물, 이미지/dist를 자동 보존하지 않는다.
이 제외 범위와 별도 보호 절차도 매뉴얼에 명시했다.

**결론: 검증된 준비물은 커밋·푸시까지 완료했다. 서버 유실에도 실제 업무가 복구되는 운영 체계는 아직 인수 전이다.**
