## Codex 교차검증 요약

**합의한 것** — 단일 노드는 S 티어 설치판으로 현실적이다. 다중 노드 전환은 데이터 계층 분리가 앱 복제보다 먼저다. PostgreSQL FTS 폴백은 설계 문서에만 있고 구현이 없다. `collaboration-service`의 다중 인스턴스 설계는 안전하고 `wiki-backend`는 조건부다.

**Codex가 새로 잡아낸 것** (전부 직접 재확인함)

| # | 발견 | 확인 결과 |
|---|---|---|
| 1 | **DB 비밀번호 폴백 함정** | 사실. `WIKI_DB_PASSWORD:keycloak`, `ORG_DB_PASSWORD:keycloak` 식으로 앱이 기본값을 갖는데 compose는 DB URL만 주입한다. `POSTGRES_PASSWORD`만 바꾸면 Java 서비스는 여전히 옛 비밀번호를 보낸다. `.env.example`도 auth·board만 안내하고 org·wiki·alm을 누락 |
| 2 | **auth JWK가 인스턴스 로컬 파일** | 사실. 파일이 없으면 RSA 키를 새로 생성해 저장한다. replica를 늘리면 서명 키가 갈리고, 볼륨을 잃으면 발급된 액세스 토큰이 즉시 전부 무효화된다 |
| 3 | **auth-server 로그인 체인이 stateless가 아님** | 사실. `spring-session` 의존성이 0건이다. OAuth2 로그인 시작과 콜백이 다른 replica로 가면 authorization request를 찾지 못한다 |
| 4 | Grafana 익명 Admin, 로그인 폼 비활성 | 사실 |
| 5 | search 재색인 상태가 프로세스 로컬 | 사실. 잡 목록과 active lock이 `ConcurrentHashMap`/`AtomicReference`다 |
| 6 | OpenSearch 인덱스가 shard 1 / replica 0 | 사실. 노드를 늘려도 분산·복제되지 않는다 |
| 7 | 컨테이너 수 전제 오류 | 내가 14~15로 잡았으나 실제 18개다 |
| 8 | deploy.yml 주석 오류 | `wiki/collaboration은 Eureka lb`라 적혀 있으나 collaboration은 Eureka에 등록하지 않고 gateway가 Docker DNS로 직결한다 |

**내가 먼저 잡고 Codex도 확인한 것** — 스케줄러 두 개(첨부 정합, 휴지통 보존)에 분산 락이 없다. Redis 소비자 이름은 인스턴스별 UUID라 다중 인스턴스에 안전하다. `--scale` 대상이 두 서비스뿐인 이유는 나머지가 `container_name`을 갖기 때문이다.

**Codex 주장 중 내가 낮춘 것** — 위 danger 콜아웃의 DLQ 추정.

# 1부. 서버 1대 온프렘

## 판정

**S 티어 설치판으로 현실적이다.** 문제는 컨테이너 개수가 아니라 자원 통제의 부재다.

- 서비스 18개, 그중 JVM 프로세스가 10개 안팎
- **힙 상한이 설정된 건 OpenSearch 하나뿐**(512MiB). 나머지 Spring 서비스 Dockerfile은 전부 옵션 없는 `java -jar app.jar`라 컨테이너마다 기본 힙(호스트 메모리 비례)을 잡는다
- compose 전체에 컨테이너별 CPU·메모리 상한과 restart 정책이 없다
- 헬스체크가 대부분 5초 간격이라 상시 부하가 얹힌다

> [!note] OpenSearch 512MiB를 서버 산정 근거로 쓰지 말 것
> 그건 힙일 뿐 RSS와 파일 캐시를 포함하지 않는다. 리포에 운영 실측값(RSS·CPU·QPS)은 없다.

## 설치판에서 반드시 바꿀 것

1. **외부 URL 계약 통일** — nginx는 `:80`에 `server_name localhost`, Keycloak은 `start-dev`에 `KC_HOSTNAME=http://localhost:8080`, realm의 redirect URI와 web origin도 전부 HTTP localhost다. TLS 종료 지점, `KC_HOSTNAME`, front issuer, `FRONTEND_URL`, realm redirect/origin, `PLATFORM_ISSUER`, CORS를 **하나의 고객 도메인으로** 맞춰야 한다. split-horizon 수동 `ClientRegistration`은 그대로 유지한다. 코드가 이미 브라우저용 front issuer와 내부 back base를 분리하고 있어 값만 갈면 된다.
2. **시크릿과 DB 계정** — 위 표의 1번이 여기 걸린다. 서비스별 DB role과 최소 권한을 만들고, 모든 `*_DB_USERNAME/PASSWORD`·OIDC secret·admin secret을 명시 주입한다. 기본값 폴백은 제거 대상이다.
3. **첨부 저장소 교체** — S3Mock을 온프렘 S3 호환 저장소로 바꾼다. 신규 업로드는 이미 S3 백엔드로 설정돼 있어 엔드포인트만 갈면 되지만, **기존 `storage_backend=LOCAL` 행을 옮길 일괄 이관기가 없다.** 이 이관기는 새로 만들어야 한다.
4. **보안 경계** — PostgreSQL·Redis·Keycloak·gateway가 호스트 포트로 공개돼 있다. OpenSearch는 보안 플러그인 off, Grafana는 익명 Admin이다. 외부 노출을 nginx/LB의 TLS 포트로 한정한다. OpenSearch 보안을 켜면 search-service의 무인증 클라이언트에도 인증 구성이 따라붙는다.
5. **패키징** — 백엔드 이미지 기본 태그가 전부 `latest`다. 설치판은 digest 고정이 원칙이다. nginx SPA 마운트가 `C:/deploy/dist`로 하드코딩돼 있어 리눅스 호스트에서 그대로 못 쓴다. GHCR pull과 로컬 `build:`가 섞여 있어 폐쇄망용 이미지 번들 절차가 별도로 필요하다.

## 그대로 둬도 되는 것

- PostgreSQL 한 인스턴스에 논리 DB 여섯 개. **단 계정은 분리한다.**
- Redis Streams와 AOF 지속화
- OpenSearch 단일 노드 (shard 1 / replica 0이라 HA는 없다는 전제 위에서)
- stdout JSON → Alloy → Loki → Grafana 구조
- gateway. 인증 조기 차단, 경로 변환, rate limit, WebSocket 프록시, 서킷브레이커를 소유하므로 단일 노드에서도 유지 가치가 크다

## 단일 장애점과 백업

호스트 자체가 최상위 SPOF이고, 그 아래 PostgreSQL·Redis·nginx/gateway·Keycloak·오브젝트 스토리지가 각각 SPOF다.

복구 단위 권고:

| 대상 | 방식 |
|---|---|
| PostgreSQL | DB별 논리 dump보다 **클러스터 물리 base backup + WAL**이 우선. 여섯 개 논리 DB를 한 시점으로 함께 복원해야 하기 때문이다. 논리 dump를 쓴다면 쓰기 중지 창에서 globals/roles까지 한 세트로 취급한다 |
| 첨부 | wikidb 메타데이터와 오브젝트를 **같은 복구 시점**으로. 이관이 끝날 때까지 legacy LOCAL 볼륨도 원본이다 |
| auth JWK | 숨은 급소. 잃으면 새 키가 생성돼 기존 액세스 토큰이 전부 무효가 된다 |
| Redis | AOF에 Streams·컨슈머 그룹·PEL이 들어 있다. 잃으면 미처리 색인 이벤트가 사라져 전체 재색인이 필요하다 |
| OpenSearch | 파생 데이터. 재색인이 정식 복구 경로라 우선순위가 낮다 |

복구 순서는 **PostgreSQL·오브젝트 스토리지·JWK → Redis → Keycloak/앱 → OpenSearch 재색인 → gateway/nginx → 관측** 이다.

## Eureka와 gateway

단일 노드에서 Eureka는 값을 하지 않는다([[30 온프렘·SaaS 배포모델 적합성 평가 + 프로젝트 구조 부채 (2026-08-29)]] S-04). gateway는 반대로 값이 크다. 둘을 같이 묶어 판단하지 않는다.

## 초기 사이징 (추정)

**8 vCPU / 32GiB / 엔터프라이즈 NVMe 1TB 이상 + 별도 백업 저장소.** 검색을 완전히 빼는 최소판은 4~8 vCPU / 16GiB 가능성이 있으나 검증이 필요하다. 리포에 실측이 없으므로 계약 용량으로 쓰기 전에 고객 데이터로 부하시험한다.

# 2부. 다중 노드 온프렘

## 쪼개는 순서

1. 첨부를 운영 S3로 전환하고 **LOCAL 데이터를 이관**
2. PostgreSQL과 오브젝트 스토리지를 앱 호스트에서 분리
3. Redis와 OpenSearch를 별도 엔드포인트로 분리
4. **auth 세션·JWK, wiki 스케줄러, search 재색인 상태를 분산 안전하게 변경**
5. 앱 수평 확장
6. 관측 분리 — 다중 호스트가 되는 순간 Alloy를 **호스트마다** 둬야 한다. 지금 Alloy 한 개는 자기 Docker 소켓의 컨테이너만 발견한다

4번을 건너뛰고 5번을 하면 인증과 데이터 정합이 깨진다. 순서를 바꾸지 않는다.

## 배포 방식

| 방식 | 판정 |
|---|---|
| compose를 여러 호스트에 수동 분할 | **비권고.** 서비스들이 Docker 내부 DNS 이름으로 직결돼 다른 호스트에서 해석되지 않는다. Eureka도 `prefer-ip-address`로 컨테이너 IP를 등록하는데 앱 포트가 호스트에 공개돼 있지 않아 타 호스트 gateway가 닿지 못한다 |
| Swarm | M 티어 과도기 선택지. overlay DNS와 replica 배치는 도움이 되지만 `container_name`·로컬 볼륨·`C:/deploy`·`build:`·`depends_on: condition`을 재작성해야 하고, **상태 계층 HA는 Swarm이 해결해주지 않는다** |
| 단일 노드 k8s | **비권고.** 번역 비용만 생기고 호스트·스토리지 SPOF는 그대로다 |
| 풀 k8s | **M/L 권고.** Service DNS·replica·rollout·secret·PVC·노드 배치·Alloy DaemonSet을 일관되게 제공한다 |

> [!important] 지원 토폴로지는 둘로 고정한다
> **S는 Compose appliance, M/L은 Kubernetes/Helm.** Swarm을 정식 세 번째 설치판으로 유지하면 테스트 조합만 늘어난다.
>
> k8s에서는 Eureka를 끄고 gateway의 모든 URI를 Service DNS로 직접 주입한다. gateway 자체는 경계이므로 유지한다.

## 수평 확장을 막는 실제 장애물

| 항목 | 판정 |
|---|---|
| wiki LOCAL 첨부 | 같은 호스트의 두 replica는 같은 named volume을 공유해 읽힌다. **다른 호스트에서는 각자의 로컬 볼륨이라 안전하지 않다** |
| 권한 Caffeine 캐시 | 인스턴스별 30초 캐시. 권한 회수 직후 두 replica가 다른 판정을 낼 수 있다. 스펙상 수용된 지연이지만 **응답 비결정성은 운영 문서에 명시**해야 한다 |
| auth-server 세션 | 로그인 웹 체인이 stateless가 아니고 `spring-session`이 없다. 공유 세션 저장소나 콜백 affinity가 선행 조건 |
| auth-server JWK | 인스턴스 로컬 파일. 공유 키 저장소 없이 replica를 늘리면 JWKS와 서명이 갈린다 |
| collaboration | **안전에 가깝다.** Redis fan-out, 인스턴스 식별자, store lock, PostgreSQL bytea 정본이 구현돼 있다. 인메모리 Map은 텔레메트리용이라 정본에 영향이 없다 |
| Redis Streams 소비 | **안전하다.** 그룹은 공통, 컨슈머 이름은 인스턴스별 UUID. XPENDING→XCLAIM, XACK, DLQ 원자 Lua가 있어 at-least-once 다중 소비에 적합 |
| 색인 멱등성 | 안전하다. 외부 버전을 쓰고 409 충돌을 성공적 no-op로 처리한다 |
| 이벤트 발행 보장 | **DB outbox가 없다.** 커밋 후 XADD가 실패하면 요청은 성공하고 이벤트만 유실된다. 전체 재색인이 유일한 복구다 ([[24 현재 아키텍처·구현 평가 + 개선 백로그 (2026-08-03)]] M-07) |
| Streams backlog | `MAXLEN ~100000`으로 잘린다. L 티어에서 소비자 장애가 길어져 이를 넘으면 stream만으로 복구를 보장할 수 없다 |
| migration worker | **안전하다.** 조건부 UPDATE 점유, claim token, lease 회수, `@Version`이 모두 있다 |
| 첨부 정합 스케줄러 | **위험.** replica마다 같은 후보를 조회하는데 분산 claim/lock이 없다. 중복 확정 이벤트나 객체 삭제 경합이 가능하다 |
| 휴지통 보존 스케줄러 | 기본 retention이 `PT0S`라 꺼져 있어 지금은 무해하다. **운영에서 켜는 순간** 단일 리더나 분산 락이 필요하다 |
| auth 토큰 정리 잡 | 모든 replica에서 매일 실행된다. DB bulk delete라 결과는 수렴하지만 불필요한 중복이다 |
| search 재색인 | **위험.** 잡 상태와 active lock이 프로세스 로컬이다. A에서 시작한 잡을 B가 찾지 못하고, 둘이 동시에 별칭 전환을 시작할 수 있다 |

같은 코드베이스 안에 **정답 패턴이 이미 있다.** migration worker의 lease가 그것이다. 첨부 정합과 휴지통 스케줄러에 그 패턴을 적용하지 않았을 뿐이다.

## `deploy.yml --scale` 판정

- **collaboration-service=2** — 정적 코드상 안전에 가깝다. 티켓 GETDEL, fan-out, store lock, DB 정본이 갖춰져 있다. Redis·PostgreSQL 장애가 곧 전체 협업 장애인 점은 남는다.
- **wiki-backend=2** — **조건부 안전.** REST는 확장되지만 인스턴스별 캐시와 무가드 스케줄러 두 개가 남는다.
- 배포 워크플로의 검증은 "기대한 수만큼 컨테이너가 healthy인가"까지다. 동시 저장·스케줄러 중복·Redis 장애 같은 **의미적 안전성은 검사하지 않는다.**

## Keycloak 다중 노드

**고정 hostname 결정 자체는 문제가 아니다.** 문제는 그 값이 `localhost`라는 것뿐이다. 되돌리지 말고 값만 바꾼다.

- 모든 replica의 `KC_HOSTNAME`을 동일한 외부 SSO URL로 고정
- 브라우저 인가와 issuer는 그 외부 URL, auth-server의 토큰·JWKS·백채널 로그아웃은 내부 Service DNS
- 수동 `ClientRegistration`의 front/back 분리는 유지
- production 캐시 스택과 노드 디스커버리, 공용 PostgreSQL, 앞단 LB/TLS

**Keycloak만 복제하면 의미가 없다.** auth-server가 여전히 로그인 진입점의 단일 장애점이고, 그걸 풀려면 위의 JWK 공유와 세션 공유가 먼저다.

# 3부. 고객 규모별

> [!caution] 아래 수치는 추정 초기값이다
> 리포에 부하시험, 동시 WebSocket 수, 문서 크기 분포, 색인 QPS 실측이 없다. 계약 용량으로 쓰기 전에 고객 데이터로 부하시험한다.

| 티어 | 가정 | 토폴로지 | 초기 하드웨어 | 먼저 오는 병목 |
|---|---|---|---|---|
| **S** | 동시 25~100명, 문서+이슈 10만 이하, 편집 room 20 이하, 첨부 0.1~1TB | 단일 Compose appliance. nginx/gateway/auth/org/wiki/alm/collaboration/PG/Redis. 통합 검색을 제공하면 search+OpenSearch 필수. board-service는 샘플이라 제외. S3Mock 제외 | 8 vCPU / 32GiB / NVMe 1TB+ + 별도 백업 | OpenSearch 힙과 디스크, PostgreSQL I/O, 여러 JVM의 baseline 메모리 |
| **M** | 동시 100~500명, 문서+이슈 10만~100만, room 20~100, 첨부 1~5TB | 데이터 계층 분리. 앱 노드 2대에 gateway/wiki/collaboration/alm/org 복제. auth는 세션·JWK 해결 후 2대. PG·Redis·오브젝트·OpenSearch를 앱과 분리 | 앱 2×(8~16 vCPU/32GiB), PG 16 vCPU/64GiB NVMe, 검색·관측 16 vCPU/64GiB NVMe, Redis HA 3노드 | 단일 PG primary, Redis 단일 엔드포인트, shard 1/replica 0, 재색인 로컬 상태 |
| **L** | 동시 500~2,000명, 문서+이슈 100만~1,000만, room 100~500, 첨부 5~50TB | 풀 k8s. 앱 replica 3+, PG HA, Redis HA, OpenSearch 데이터 노드 3+, 분산 오브젝트 스토리지, Alloy DaemonSet + 중앙 Loki/Grafana. Eureka는 Service DNS로 대체 | 앱 3×(16/64), PG 3×(16~32 / 64~128), OpenSearch 3×(16~32 / 64~128 + 로컬 NVMe), Redis 3×(8/32) | PG write·커넥션, Redis Streams·pub/sub, 활성 Y.Doc 메모리, shard 구조, gateway·auth 경계 |

> [!warning] M/L로 갈 때 인덱스 설정을 함께 바꿔야 한다
> 현재 매핑이 shard 1 / replica 0이라 **노드만 추가해도 분산도 복제도 되지 않는다.** 인덱스 세대별 shard/replica 정책이 함께 가야 한다.

## 티어별 검색 선택지

| 선택 | 실제 결과 |
|---|---|
| 검색 켬 | search-service + OpenSearch를 함께 켠다 |
| 검색 끔 | 통합 검색이 사라지고 해당 경로가 5xx가 된다. compose가 route 단위로 격리한다고 명시하고 있어 **다른 기능은 살아 있다** |
| PostgreSQL FTS | **현재 선택 가능한 옵션이 아니다.** 설계 문서 15번의 폴백은 구현되지 않았다 |
| ALM 통합 검색 | **현재 제품 기능이 아니다.** 위 danger 콜아웃 참조 |

**서비스를 합치는 것은 권하지 않는다.** S에서는 같은 호스트에 co-location만 하고, M/L에서 데이터·검색·관측을 물리적으로 분리하는 방향이 맞다.

## 다중 노드 출시 선행 조건

현재 코드 상태에서 M/L 설치판을 내려면 아래가 먼저 닫혀야 한다. 순서대로다.

1. **LOCAL 첨부 이관기** — 없다. 새로 만들어야 한다
2. **auth-server JWK 공유 + 세션 공유(또는 콜백 affinity)** — 이게 안 되면 auth를 복제할 수 없고, 그러면 로그인이 단일 장애점으로 남는다
3. **wiki 스케줄러 단일 실행** — migration worker의 lease 패턴을 첨부 정합과 휴지통 보존에 적용
4. **search 재색인 분산 락과 상태 외부화**
5. **ALM 검색 브랜치 머지 + proto 버전 정합** — [[30 온프렘·SaaS 배포모델 적합성 평가 + 프로젝트 구조 부채 (2026-08-29)]] S-01과 같은 뿌리다

단일 노드(S) 설치판은 이 다섯 개 없이도 낼 수 있다. 1번과 5번만 있으면 된다.
