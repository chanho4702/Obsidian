## 1부. 무엇을 했나 — 쉽게 설명하면

### 듀얼모드: 스위치 하나로 두 개의 뒷단

프론트의 `wikiStore`는 화면이 데이터를 요청하는 **단일 창구**다. `listSpaces()`, `createPage()`, `updatePage()` 같은 함수 이름과 의미가 계약으로 고정돼 있다.

이번에 한 일은 그 창구 뒤에 **구현체를 하나 더** 놓은 것이다.

```
화면(React)  →  wikiStore(계약 고정)  ┬─ wikiMock.ts    (localStorage)
                                      └─ wikiApi.ts     (fetch → wiki-backend)
```

어느 쪽을 쓸지는 빌드 시점 환경변수가 정한다:

```ts
export const USE_BACKEND =
  Boolean(import.meta.env.VITE_API_PROXY) || Boolean(import.meta.env.VITE_API_BASE);
```

- **아무것도 설정 안 함** → 목업. 테스트·CI·오프라인 개발이 여기 산다.
- **`VITE_API_PROXY` 설정** → dev 서버가 `/api`·`/oauth2`·`/login`을 게이트웨이로 프록시. 브라우저 입장에선 same-origin이라 **CORS가 아예 발생하지 않는다** — 프로덕션 nginx([[11 nginx 통합배포 + 3앱 SSO (2026-07-14)|11번]])와 동일한 모양이다.
- **`VITE_API_BASE` 설정** → 절대 URL로 직접 크로스-오리진 접속(게이트웨이 CORS + 쿠키 SameSite 설정이 별도로 필요).

> [!note] 왜 목업을 안 지웠나
> 목업을 지우면 테스트 443개가 전부 "백엔드가 떠 있어야 통과하는 테스트"가 된다. CI에 Postgres·Keycloak·org-service·게이트웨이를 다 띄우거나, 아니면 테스트를 fetch 모킹으로 전부 다시 쓰거나 — 둘 다 비싸다. 목업을 남기면 **마이그레이션 리스크가 백엔드 모드 안에 격리**된다.

### 경계 매퍼: 두 세계의 말이 다르다

백엔드와 프론트는 같은 개념을 다르게 부른다. 이 번역을 화면 곳곳에 흩어두면 나중에 필드 하나 바뀔 때 전수조사를 해야 한다. 그래서 **순수 함수 한 파일**(`store/mapping.ts`)에 몰아넣었다 — 부수효과 없음, 그래서 단위 테스트가 쉽다.

| 개념 | 백엔드 | 프론트 | 경계에서 하는 일 |
|---|---|---|---|
| id | `Long`(숫자) | `string` | `String(id)` ↔ `Number(id)`. 정수가 아니면 즉시 throw |
| 페이지 본문 | `content` | `body` | 이름만 바꿔 옮김 |
| 페이지 버전 | `version: int` | (없었음) | `Page.version` 신설 → 낙관적 락의 재료 |
| 형제 순서 | **없음** | `position` | 서버에 안 남는다(아래 참조) |
| 버전 이력 | `editedBy`/`createdAt` | `savedBy`/`savedAt` | 필드 매핑 |
| 에러 | `{ "error": "..." }` + 상태코드 | 한국어 예외 | 응답 `error`를 한국어 문구로, 없으면 상태코드별 폴백 |

**id 타입이 다른 게 왜 문제냐**면, JS에서 `"12" === 12`는 거짓이기 때문이다. 트리에서 부모를 찾을 때 `parentId === page.id`로 비교하는 코드가 한 군데라도 숫자와 문자열을 섞으면 그 노드는 조용히 트리에서 사라진다. 그래서 **프론트 타입은 전부 string으로 통일**하고, 백엔드로 나가는 순간에만 숫자로 되돌린다.

### 낙관적 락을 화면 변경 없이 통과시키기 — 그리고 그 대가

백엔드는 `PUT`에 `expectedVersion`을 요구하고, 안 맞으면 **409 Conflict**를 낸다([[17 Wave B — wiki-backend 구현기록, 과정과 원리 해설 (2026-07-21)|17번]]). 문제는 프론트의 `updatePage(id, patch)` 시그니처에 version 자리가 없다는 것이었다.

"화면 무수정"을 지키려고 어댑터가 **저장 직전에 `getPage`로 현재 version을 읽어서** `expectedVersion`에 실었다. 동작은 한다. 그런데 이게 **낙관적 락의 의미를 없앤다**:

- 낙관적 락의 목적은 "내가 **편집을 시작할 때** 본 버전"과 "지금 서버 버전"이 다르면 막는 것이다.
- 어댑터가 읽는 건 **저장 시점의 최신 버전**이다. 그 사이 남이 저장했어도 최신값을 그대로 실어 보내니 서버는 항상 통과시킨다 → **last-write-wins**(나중에 저장한 사람이 남의 편집을 덮어씀).

이건 최종 리뷰에서 발견돼 **알려진 한계로 기록**됐다(설계 §9-1). 진짜로 고치려면 편집 화면이 로드 시점의 version을 들고 있다가 넘겨야 하는데, 그건 "화면 무수정" 스코프 밖이라 후속으로 뺐다.

> [!tip] 여기서 배운 것
> "화면을 안 고치겠다"는 제약은 **어댑터가 정보를 지어내게 만든다.** 없는 정보(로드 시점 version)를 어댑터가 대신 만들어내면, 계약은 만족하지만 기능은 죽는다. 계약을 지킨 것과 목적을 달성한 것은 다르다.

### 형제 순서는 서버에 안 남는다

백엔드 트리는 `{id, parentId, title}`만 준다 — `position`이 없다. 페이지 이동도 `PUT`으로 `parentId`만 바꾼다. 그래서 **드래그로 순서를 바꿔도 서버엔 부모 변경만 남고 순서는 안 남는다.** 이건 숨기지 않고 결정으로 명시했다(설계 §7-4): 수용하고, `wiki-backend`에 `position` 컬럼 추가는 후속 티켓.

### 없는 것들: 사용자 이름, 댓글

- **사용자 이름/아바타** — wiki-backend에 User 테이블이 없다. JWT의 `sub`는 숫자 id고, 이름은 org-service가 안다. 현재 사용자만 `/api/me`로 이름을 얻고, 나머지는 `사용자 #{id}` 폴백. org-service의 users API 노출은 후속.
- **댓글** — 백엔드에 없다. localStorage 목업을 **별도 모듈로 분리해서 유지**한다. 백엔드에서 온 페이지 id를 키로 쓰므로, 백엔드 데이터와 목업 댓글이 한 화면에 공존한다.

### 503 전파 — "비어 있음"과 "고장남"은 다르다

이게 이번 작업에서 가장 값진 발견이다.

wiki-backend는 권한을 스스로 판정하지 않고 org-service에 gRPC로 물어본다. 그리고 org-service가 죽으면 **fail-closed**(모르면 거부)로 동작한다 — 인가에서는 옳은 기본값이다.

그런데 목록 API에서 이게 이상하게 나타났다. `accessibleSpaces`가 "권한 확인 실패 → 접근 가능한 스페이스 없음 → **빈 배열**"을 반환했다. 프론트가 받는 건 `[]`다. 화면은 "스페이스가 하나도 없네요"라는 **정상 빈 상태**를 그린다.

**사용자는 자기 문서가 전부 사라졌다고 본다.** 실제로는 권한 서비스가 죽었을 뿐인데.

```
org-service 다운
   → gRPC UNAVAILABLE
      → (전) 빈 배열 반환 → 프론트 "스페이스가 없습니다"   ← 거짓말
      → (후) 503 ServiceUnavailable → 프론트 "일시적으로 불러올 수 없습니다 [다시 시도]"
```

수정은 **장애의 종류를 구분**하는 것이었다(`5d39c50`):

- `UNAVAILABLE` · `DEADLINE_EXCEEDED` = **전송 장애**(상대가 없거나 못 닿음) → `ServiceUnavailableException` → **503으로 전파**. "판정을 못 했다"는 사실을 위로 올린다.
- 그 외(`INTERNAL` 등) = **판정은 했는데 뭔가 잘못됨** → 기존대로 fail-closed(거부).

프론트도 같이 고쳤다(`a4c6c9f`). `App`이 `listSpaces` 실패를 빈 목록으로 삼키지 않고 **에러 화면 + "다시 시도"**로 노출한다.

> [!important] 일반화하면
> **fail-closed와 "조용한 빈 결과"는 다른 것이다.** 단일 리소스 조회에서 fail-closed는 403이 되어 사용자에게 보인다. 하지만 *목록* API에서 fail-closed를 빈 배열로 구현하면, 실패가 **성공적인 빈 상태로 위장**된다. 목록을 반환하는 모든 권한 필터링 지점에서 이 함정을 확인할 것.

### 최종 리뷰가 잡은 것 — 전부 백엔드 모드 전용

브랜치 전체 리뷰 판정은 "With fixes". 목업 모드는 블로커 0건(443 green, 코드가 verbatim 이동했음이 확인됨). Important 3건은 모두 **`VITE_API_BASE`를 설정했을 때만 나타나는** 것들이었다:

1. **낙관적 락 무력화** (위 §1부)
2. **"Invalid Date"** — 백엔드 `SpaceResponse`·`PageResponse`에 시각 필드가 없어 매퍼가 `""`를 넣는다. 화면이 `new Date("").toLocaleDateString()`을 부르면 `Invalid Date`가 그대로 렌더된다.
3. **복원이 항상 "변경 없음"** — HistoryModal의 no-op 판정이 `restored.updatedAt === page.updatedAt`인데 백엔드 모드에선 둘 다 `""`라 항상 참. 실제로 복원됐는데 "현재 내용과 동일합니다" 토스트가 뜬다.

이 브랜치는 "화면 무수정" 스코프였으므로, 리뷰는 **코드 대신 문서를 고치게** 했다: 매퍼의 주석에 허위 주장(실제로 하지 않는 `"-"` 표기)을 제거하고, 설계 문서에 §9 "Backend-mode 알려진 한계"를 신설했다.
