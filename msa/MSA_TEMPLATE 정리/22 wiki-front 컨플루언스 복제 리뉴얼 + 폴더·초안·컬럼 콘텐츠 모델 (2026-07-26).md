## 1부. 콘텐츠 모델 세 결정 — 무엇을 버렸나

### 결정 1. 폴더는 새 엔티티가 아니라 `Page.type` 필드

**문제**: 계층이 `Page.parentId` 하나뿐이라 **묶는 껍데기**와 **읽는 문서**가 구분되지 않았다. 목차 역할만 하는 페이지도 본문·버전·댓글을 갖고, 트리에서 문서와 똑같은 아이콘으로 보인다. 사용자는 제목으로 추측해야 한다.

**두 갈래**:

| | 별도 엔티티 `Folder` | `Page.type: "page" \| "folder"` |
|---|---|---|
| 모델 순수성 | 높음 — 폴더가 body·버전을 안 가짐 | 낮음 — 형식적으로 갖게 됨 |
| 변경 범위 | 트리·이동·검색이 **두 타입을 합쳐 다뤄야** 함 | `parentId`·`movePage`·트리 **전부 재사용** |
| 백엔드 | 새 테이블 + 새 API | **컬럼 하나** |

**채택: 필드.** 대가(폴더가 안 쓰는 필드를 형식적으로 가짐)를 **화면·스토어 계약으로 강제**해 막는다 — 폴더에는 편집 경로 자체를 만들지 않았다.

여기서 실제로 값을 한 장치가 `lib/contentPath.ts`다. 링크 목적지가 타입마다 갈리므로(`/pages/{id}` vs `/folder/{id}`) **한 곳으로 모았다**. 커밋 메시지가 이유를 정확히 적어뒀다:

> 한 군데라도 `/pages/{id}`로 하드코딩하면 폴더를 눌렀을 때 빈 문서가 열린다.

타입이 늘어난 순간, **"목적지 계산"이 흩어져 있으면 무음 버그가 된다.** 타입 분기를 도입할 때 같이 도입해야 하는 것은 분기 그 자체가 아니라 분기를 모아두는 함수다.

**구분은 아이콘 + 텍스트 둘 다.** `"운영 문서 (폴더)"` 형태로 접근 이름에 타입을 넣었다. 아이콘만으로 구분하면 WCAG 1.4.1(색·형태만으로 정보 전달 금지) 위반이고, 스크린리더에는 아무것도 안 들린다.

### 결정 2. 초안은 `Page.status` — 그리고 백엔드 모드에서는 **명시적으로 거부**한다

`Page.status: "draft" | "published"`. 사이드바 "+"가 초안을 **즉시 만들어** 트리에 `초안` 배지와 함께 세우고 편집 화면을 연다. 초안의 주 액션은 "업데이트"가 아니라 "게시".

이 결정에서 가장 중요한 부분은 기능이 아니라 **백엔드가 아직 이걸 모른다**는 사실을 다루는 방식이다. `type`·`status`는 목업 모드에만 산다([[20 프론트-백엔드 듀얼모드 연동 — 경계 매퍼·낙관적 락·503 전파 (2026-07-22)|20번]]의 듀얼모드). 어댑터에서 세 지점이 이렇게 처리된다:

- `createPage` — 두 값을 요청에 **싣지 않는다**(백엔드가 모르는 필드)
- `mapPage` — 응답을 전부 `page`/`published`로 읽는다
- `publishPage` — **"이 서버는 아직 초안/게시를 지원하지 않습니다"로 거부한다**

> [!important] 세 번째가 핵심이다
> 조용히 성공한 척하면 사용자는 게시된 줄 알고 화면을 떠나지만 **문서는 초안으로 남는다.** 미지원 기능은 실패해야 하고, 그 실패는 보여야 한다. [[20 프론트-백엔드 듀얼모드 연동 — 경계 매퍼·낙관적 락·503 전파 (2026-07-22)|20번]]의 "503을 빈 배열로 삼키던" 버그와 정확히 같은 종류의 함정이다 — **실패를 성공적인 상태로 위장하지 말 것.**

백엔드에 컬럼이 붙으면 **이 세 지점만** 바꾼다.

### 결정 3. 컬럼(레이어 분할)은 블록 JSON이 아니라 `:::` 확장 문법

wiki-front의 불변조건 2는 **"`Page.body`는 마크다운 문자열"**이다. "한 줄에 좌/우를 나란히"는 마크다운으로 표현할 수 없는 구조라, 로드맵에 `⚠️ 저장 포맷 재논의` 플래그가 걸려 있던 항목이었다.

**버린 대안: 블록 JSON.** 본문을 구조화된 JSON으로 바꾸면 컬럼이든 뭐든 표현할 수 있다. 대신 **백엔드 계약·버전 diff·`[[위키링크]]` 파이프라인이 전부 다시 만들어져야 한다.**

**채택: 컨테이너 확장 문법.**

```
::::columns
:::column
왼쪽 내용
:::
:::column
오른쪽 내용
:::
::::
```

- `body`는 계속 마크다운 문자열 → **백엔드 계약·diff·링크 파이프라인 무변경**
- 중첩은 "바깥 마커가 더 길다" 규칙 — `markdown-it-container`·`remark-directive`의 공통 관례
- **대가**: GFM 표준이 아니다. 이 문법을 모르는 렌더러(GitHub 등)에서는 `:::` 줄이 텍스트로 보인다. **내용은 사라지지 않는다** — 이게 JSON 대비 결정적 차이다.

구현상 주의: **편집 경로(`markdown-it` 컨테이너 규칙)와 보기 경로(`remark-directive`)가 같은 문자열을 같은 구조로 읽어야 한다.** 한쪽만 고치면 저장했다 열 때 구조가 깨진다.

## 2부. 컨플루언스 복제 — 셸부터 다시

### 셸 통일: 화면마다 다른 레이아웃을 하나로

문제는 **사이드바 토글이 나타났다 사라졌다** 하는 것이었다. 홈·디렉토리는 `WikiTopBar`만, 스페이스는 `WikiLayout`(사이드바 포함) — 셸이 라우트마다 달랐기 때문이다.

`WikiLayout`을 해체해 둘로 나눴다(`810abe6`):

- **`AppShell`** — **모든** 라우트를 감싼다. 헤더(토글 상시 + "만들기") + 접힘형 사이드바 + `<Outlet/>`. 스페이스 라우트에서 페이지 트리를 로드해 `WikiOutletContext`를 사이드바와 하위 화면에 **함께** 공급한다. 존재하지 않는 spaceId면 첫 스페이스로 리다이렉트.
- **`GlobalSidebar`** — 3단 구성. ① 글로벌 네비(추천·최근·별표·스페이스·앱) ② **컨텍스트 섹션**: 스페이스 안이면 [스위처 + 별표 목록 + 페이지 검색 + PageTree], 홈·디렉토리면 [별표 목록 + 모든 스페이스 보기] ③ 리사이저.

즉 **셸은 고정, 사이드바의 가운데 층만 라우트에 따라 바뀐다.**

> [!tip] 458 테스트가 한 줄도 안 바뀌고 통과했다
> 레이아웃을 통째로 갈아엎었는데 테스트 이관이 0건이었던 이유는, 기존 테스트가 **DOM 구조가 아니라 `role` + `aria-label`로 쿼리**하고 있었기 때문이다. `GlobalSidebar`가 구 사이드바의 **접근성 계약**(스위처 트리거, 별표 region, 페이지 검색, 트리, 리사이저, 접힘 시 미렌더)을 그대로 재현하도록 설계했더니 구조 변경이 테스트에 안 보였다.
>
> 일반화: **접근성 쿼리로 쓴 테스트는 리팩터링에 강하다.** `getByTestId`나 CSS 셀렉터로 썼다면 전부 다시 써야 했다.

### 홈 대시보드와 디렉토리

- **`/home`**(`6423c06`) — "마지막 작업하던 곳에서 다시 시작" 카드. 클라이언트 방문 로그(`lib/recentVisits`)에 `PageViewPage`가 부수효과로 기록하고, `relativeTime`으로 "N분 전"을 표시. 백엔드 활동 피드는 `listVersions` 기반 후속 슬라이스로 미룸.
- **`/spaces`**(`c67a6c8`, `79193f3`) — 캡처대로 **"자주 찾는 스페이스"는 카드**, **"모든 스페이스"는 테이블**(이름·Labels·Owner·Actions). 카드는 정사각 아이콘 타일(좌상) + 별표(우상) + 이름 세로 배치.

여기서 **의도적으로 안 만든 것**이 있다. 캡처에 있는 `모든 분류 ▾`·`모든 필터 ▾` 드롭다운과 Actions의 눈·⋯ 아이콘이다. 백엔드가 labels/owner를 안 주므로 넣으면 **죽은 컨트롤**이 된다. 충실 복제를 위해 동작하지 않는 UI를 깔지 않는다 — 대신 "왜 없는지"를 리뷰 문서에 기록해 무음 누락과 구분했다.

같은 원칙이 폴더 기획에도 적용됐다: 캡처의 "만들기" 메뉴에 있는 **라이브 문서·화이트보드·데이터베이스·스마트 링크는 비활성 항목으로도 넣지 않는다.**

### 디자인 재검토 2회 — 코드 무수정 리뷰가 먼저

디자이너 롤이 **코드를 고치지 않고** 캡처 대조 리뷰만 두 번 돌렸다(07-22, 07-25). 근거 표기는 `캡처명 / 토큰 / WCAG / 파일:라인` 형식.

1차(`d5acaad`)에서 반영된 것:

- **팝오버 그림자 하드코딩 5곳** → `var(--chanho-shadow-overlay)`. 다크모드에서 그림자가 소실되던 문제 해소.
- **`--wiki-text-subtlest` 대비** `#8993a4`(3.1:1) → `#626f86`(≈5.08:1). WCAG 1.4.3 통과.
- 텍스트 글리프 → lucide 아이콘(`PanelLeft`, `Star`).
- 사이드바 **스코프 정리** — 스페이스 사이드바에 있던 별표목록·디렉토리 링크를 홈·디렉토리 컨텍스트로 이관.

2차(07-25)는 사용자가 콕 집은 3가지(디렉토리·에디터·폴더/페이지 구분)에 집중했고, **1차에서 이미 처리된 항목은 재지적하지 않았다**(문서 상단에 "정합"으로 명시). 리뷰가 리뷰를 반복하지 않게 하는 장치다.

### 접근성·시각 폴리시 정비 (`4cdb1fa`)

개별 화면이 아니라 **시스템적으로 빠져 있던 층**을 채웠다.

- **`prefers-reduced-motion`** — 상태 전환(`transition`)만 전역 무력화하고 **`animation`은 일부러 안 건드렸다.** 이 앱의 keyframe은 전부 진행 표시(Spinner·스켈레톤)라, 멈추면 **로딩이 중단된 것처럼 보인다.** 대신 개별 감속. → *"reduced-motion은 모든 움직임을 끄는 게 아니라, 정보를 전달하지 않는 움직임을 끄는 것"*
- **`color-scheme: light dark`** — 다크모드에서 **네이티브** 스크롤바·select 팝업·autofill이 흰색으로 남아 명도가 튀던 문제. CSS로는 못 고치는 영역이라 브라우저에 알려줘야 한다.
- **스킵 링크**(WCAG 2.4.1) + 앱 로컬 커스텀 컨트롤 20개 셀렉터의 **포커스 링을 DS 토큰으로 통일**.
- 하드코딩 duration 3개 제거, **스켈레톤 로딩**(Spinner만으로는 로드 완료 시 레이아웃이 밀림), 날짜·버전·diff에 `tabular-nums`, `100vh`→`100dvh` 폴백.
- **`<main>` 랜드마크 중첩 제거** — 셸이 이미 `main`인데 페이지가 또 `main`을 그리고 있었다.

## 3부. 코드·테스트가 통과했는데 화면이 틀렸던 것 (`109b94a`)

MVP 구현 후 **실제 브라우저로 확인**했더니 결함 3건이 나왔다. 셋 다 자동 테스트가 통과한 상태였다.

**① 2열을 만들면 오른쪽부터 타이핑됐다.**
`setColumns` 삽입 직후 커서가 마지막 열에 놓였다. 인수조건 C1("첫 열에 커서가 놓인다") 위반. 기존 테스트는 **직렬화 결과만** 검증했다 — 마크다운 문자열은 정확했으니 통과한다. 커서 위치는 문자열에 안 나타난다.
→ 커서가 첫 열 **안에** 있는지 검증하는 테스트를 추가했다.

**② 폴더 배너 제목이 `"제목 없는 폴/더"`로 잘렸다.**
`.folder-banner-body`가 flex인데 heading에 `flex: 1`이 없어 콘텐츠 폭으로 줄어들었다. **CSS flex 기본값이 만든 줄바꿈** — jsdom 테스트에는 레이아웃 계산이 없으므로 원리적으로 못 잡는다.

**③ 스페이스 개요의 "최근 업데이트"가 폴더를 문서 아이콘으로 그렸다.**
같은 항목이 트리에서는 폴더, 개요에서는 문서로 보였다. 타입 분기를 **한 화면에서 빠뜨린** 전형적 케이스 — 결정 1의 `contentPath` 교훈이 아이콘에도 적용됐어야 했다.

함께 고친 것: **스킵 링크를 `:focus-visible` → `:focus`로.** `focus-visible`은 "키보드로 온 포커스인가"를 휴리스틱으로 판단하는데, **프로그램적 `focus()`에서는 안 걸릴 수 있다.** 그러면 링크가 숨은 채 포커스만 받아 "포커스가 어디로 갔는지 모르는" 최악의 상태가 된다.

> [!warning] 정리
> jsdom 테스트가 검증하는 것은 **DOM 구조와 이벤트 결과**다. 커서 위치, flex 계산, 시각적 구분은 그 밖에 있다. 508개가 그린이어도 **브라우저 실측은 별도 게이트**다.

## 4부. 생성 버튼 통일 (`dc7c920`) — "눌리긴 한 건가"

**증상**: 생성 버튼을 눌러도 트리에 아무것도 안 나타난다.

**원인**: 진입점이 5개인데 동작이 갈렸다. 사이드바 "+"만 초안을 즉시 만들었고, 나머지(헤더 만들기→페이지, 트리 행의 +, 폴더 화면 "페이지 만들기", 개요 "새 페이지"·"첫 페이지 만들기")는 `/pages/new` — **아직 존재하지 않는 문서** — 로 이동만 했다.

→ 전부 `useCreateDraft` 하나로 통일. 커밋 메시지가 이유를 정확히 적었다:

> 진입점마다 다르게 동작하면 "어디서 만들었냐"에 따라 트리에 보였다 안 보였다 한다.

**딸린 문제와 해법**: 누르는 즉시 문서를 만들면 실수로 누른 만큼 "제목 없음"이 트리에 쌓인다.
→ **손대지 않은 초안**(제목 그대로 + 본문 비어 있음)은 "닫기" 시 지운다. 제목이나 본문을 건드렸으면 **사용자의 작업물**이므로 초안으로 남긴다.

`/pages/new` 라우트는 **유지**한다 — 부재 위키링크 `[[제목]]`이 제목을 프리필해 여는 경로다. 쓰이지 않는 것처럼 보이는 라우트를 지우기 전에 **누가 그 URL을 만들어내는지** 확인해야 한다.

같은 커밋에서 A4(폴더 이동·삭제)도 처리했다. **이동은 이미 동작했다** — 폴더도 `Page`라 `movePage`가 타입을 가리지 않는다(결정 1의 배당금). 회귀 방지 테스트만 추가.
