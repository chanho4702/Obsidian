## 1부. 온프렘 — 방향은 맞고 실장이 개발용에 머물러 있다

온프렘은 이미 확정된 최종 목표다. [[15 ALM·Wiki 백엔드 요구사항 + 서비스 분할 설계 (2026-07-19)]]이 "ALM·Wiki를 온프렘 설치·운영 가능한 제품 형태로"를 목표로 못박았고, PostgreSQL 통일도 OpenSearch 선택(Apache 2.0 라이선스 리스크 회피)도 그 결정에서 파생됐다. `alm-front` 로드맵은 제품 포지셔닝을 **온프렘 지라 대체**로 확정했다(2026-08-28).

그래서 "온프렘에 부적합하다"는 진단은 정확히는 **설계 결함이 아니라 미완 항목**이다. 아래는 설치판을 뽑기 전에 반드시 닫아야 하는 것들이다.

| # | 항목 | 현재 상태 | 근거 |
|---|---|---|---|
| O-01 | 배포 경로가 GitHub 종속 | `repository_dispatch` → self-hosted runner → GHCR pull → 프론트는 `gh run download` | `.github/workflows/deploy.yml` |
| O-02 | 외부 IdP 의존 | Keycloak realm에 google identity provider | `infra/keycloak/realm-export.json` |
| O-03 | Keycloak이 개발 모드 | `command: start-dev --import-realm` | `infra/keycloak/docker-compose.yml` |
| O-04 | TLS 없음 | nginx가 `listen 80`만, 인증서 경로 없음 | `infra/nginx/default.conf` |
| O-05 | 첨부 저장소가 목업 | `adobe/s3mock` — compose 주석에 "운영 object storage로 사용하지 않는다" 명시 | 같은 파일 |
| O-06 | OpenSearch 보안 플러그인 비활성 | `DISABLE_SECURITY_PLUGIN: "true"` · 주석에 이미 온프렘 과제로 등재 | 같은 파일 |
| O-07 | 단일 머신 all-in-one | Postgres 인스턴스 하나가 keycloak·authdb·boarddb·orgdb·wikidb·almdb를 겸함. 백업·이중화 절차 없음 | `infra/keycloak/init-authdb.sql` |
| O-08 | 시크릿 평문 | `.env` 파일, DB 비밀번호 기본값 존재 | `infra/keycloak/.env.example` |
| O-09 | 호스트 환경이 배포에 박힘 | Windows 예약 포트 회피, PowerShell 스텝, `C:\deploy\dist` 경로, KC_HOSTNAME 고정 | `deploy.yml`, split-horizon 결정 |

> [!note] O-01은 갈아탈 대상이 명확하다
> 사내 레지스트리(Harbor 등) + 사내 CI로 이미지와 dist를 공급하는 경로. 폐쇄망이면 오프라인 이미지 번들이 추가로 필요하다. [[13 백엔드 컨테이너화 + compose 통합 — CI-CD Wave 1 (2026-07-15)]]의 계약은 그대로 두고 공급원만 바꾸는 형태가 된다.

**미결** — 인터넷이 되는 사내 서버인지 완전 폐쇄망인지, 단일 고객 설치인지 반복 납품 배포판인지가 정해지지 않았다. 이 둘이 O-01과 O-02의 작업량을 크게 가른다.

## 2부. SaaS — 싱글 테넌트가 확정 결정이자 스키마에 박혀 있다

온프렘보다 훨씬 멀다. 온프렘이 미완 항목 채우기라면 SaaS는 **확정 설계 결정을 뒤집는 일**이다.

### 근거는 주석 한 줄에 그대로 있다

```sql
-- 조직/팀/권한 스키마. 싱글 테넌트 전제(15번 문서 확정) — organization 테이블 없음.
```

`platform-backend/org-service/src/main/resources/db/migration/V1__init.sql` 첫 줄이다. 이름이 org-service일 뿐 **조직 하나**를 모델링한 것이고, 테넌트 루트 엔티티가 없다. 백엔드 소스 전체에 `tenant` 문자열이 0건이다.

### 그 전제가 스키마에 굳어 있다

| 굳은 지점 | 내용 |
|---|---|
| 키가 전역 유일 | `space.key` UNIQUE, `project_key` UNIQUE, `issue_key` UNIQUE. 두 고객사가 나란히 `DEV` 스페이스를 만들 수 없다 |
| 권한 원장에 테넌트 축 없음 | `grant_entry`의 UNIQUE는 (주체타입, 주체, 리소스타입, 리소스). 테넌트 경계를 강제할 자리가 없다 |
| 사용자 식별자 | `member.id`가 auth-server user id(JWT sub)를 그대로 PK로 쓴다 |
| IdP | Keycloak realm이 `sso-demo` 하나 |

### SaaS 고유 요구가 통째로 없다

셀프 가입·온보딩, 구독·과금·미터링, 테넌트별 쿼터와 격리, 감사 로그. 게이트웨이 레이트리밋도 테넌트가 아니라 XFF 실IP 기준이다([[19 게이트웨이 평가 + rate-limit XFF 수정 + Loki 로그 관측 스택 (2026-07-20)]]). 감사 로그는 `alm-front` 로드맵에 백로그로만 올라 있다.

### 갈림길 — 멀티테넌시를 어디서 자르나

| 방식 | 비용 | 평가 |
|---|---|---|
| 인스턴스 격리형 (고객당 스택 1벌) | 낮음 | **현실적.** 지금 구조를 그대로 재활용하고 온프렘 설치판 작업과 대부분 겹친다 |
| 스키마 분리 (테넌트당 schema) | 중간 | 커넥션·마이그레이션 운영이 테넌트 수에 비례해 늘어난다 |
| 공유 테이블 + tenant_id | 높음 | 모든 테이블·모든 쿼리·모든 인덱스 수술. 지금 규모에서 비권장 |

> [!important] 이건 기술 판단 이전에 제품 판단이다
> 온프렘 지라 대체라는 포지셔닝에서 싱글 테넌트가 파생됐다. SaaS로 간다면 **포지셔닝부터** 다시 정하는 게 먼저다. 병행이면 인스턴스 격리형이 사실상 유일한 답이고, 대체면 스키마부터 다시 볼 값어치가 있다.

## 3부. 프로젝트 구조 부채 (운영 제외)

서비스 경계는 도메인과 맞고 자의적이지 않다. 위키·ALM·조직권한·검색·협업이 각각 따로 스케일하거나 끌 이유가 있는 단위다. DB도 인스턴스 하나에 **서비스별 논리 DB**로 갈라두고 Flyway가 각자 스키마를 잡아, 서로 남의 테이블을 보지 않는다. 나중에 물리 분리해도 코드가 안 바뀐다. 권한 원장을 org-service 한 곳으로 모으고 위키의 `page_restriction` 같은 도메인 고유 제약만 각자 갖는 분리도 옳다.

부채는 **공유물이 갈라져 있다**는 한 문장으로 요약된다.

### - [ ] S-01 · common-proto가 세 갈래 버전으로 갈라져 있다

| 소비자 | 방식 | 물고 있는 버전 |
|---|---|---|
| org-service, search-service | 인리포 Gradle 프로젝트 의존 | 항상 HEAD |
| wiki-backend | GitHub Packages 아티팩트 | 0.9.0 고정 |
| alm-backend | `commonProtoVersion` 프로퍼티, 기본값 | 0.6.0 |

같은 계약의 세 세대가 동시에 돈다. 이벤트 스키마를 건드릴 때 무엇이 깨지는지 판단할 근거가 없다. 멀티레포에서 **가장 먼저** 손볼 지점이다.

**해야 할 일** — 발행 버전을 단일 원장으로 올리고 전 소비자를 같은 버전으로 맞춘다. 인리포 소비자(org·search)가 HEAD를 보는 한 발행본과의 드리프트는 계속 생기므로, 인리포도 발행 아티팩트를 소비하거나 릴리스 시 버전 고정을 강제해야 한다.

### - [ ] S-02 · 부트스트랩이 다섯 번 복사돼 있다

`SecurityConfig`, `AudienceValidator`, `ApiExceptionHandler`가 wiki-backend·alm-backend·org-service·search-service·board-service **다섯 곳에 각각** 존재한다. org-service와 wiki-backend의 `AudienceValidator`를 패키지명만 정규화해 diff하면 **javadoc 한 줄** 차이다.

토큰 검증 정책을 바꾸면 다섯 군데를 고쳐야 하고, 한 곳을 빠뜨리면 그게 곧 인증 구멍이다.

**해야 할 일** — 공용 스타터 모듈(`platform-spring-boot-starter` 성격)로 추출해 common-proto와 같은 경로로 배포한다. S-01을 먼저 정리해야 배포 경로를 재사용할 수 있다.

### - [ ] S-03 · 디자인시스템이 세 프론트를 못 덮는다

| 프론트 | @chanho/react | @chanho/tokens |
|---|---|---|
| wiki-front | 0.5.0 | 0.3.0 |
| alm-front | 0.3.0 | 0.2.0 |
| myFront | 미사용 (MUI 9) | 미사용 |

두 세대가 벌어져 있고, 한 앱은 아예 다른 UI 라이브러리를 쓴다. 배포 방식도 형제 폴더 상대경로 tarball(`file:../design-system/artifacts/*.tgz`)이라 리포를 나란히 체크아웃하지 않으면 설치가 깨진다.

지금 상태는 공유 시스템이라기보다 **wiki-front 전용에 alm-front가 옛 버전으로 얹혀 있는** 모양이다.

**해야 할 일** — 레지스트리 배포로 전환하고 두 프론트 버전을 맞춘다. myFront는 대상에서 뺄지(포트폴리오 사이트라 성격이 다름) 결정이 필요하다.

### - [ ] S-04 · Eureka 유지 판단을 설치판 시점에 재확인

[[15 ALM·Wiki 백엔드 요구사항 + 서비스 분할 설계 (2026-07-19)]]이 이미 판정했다. 온프렘 M 규모는 컨테이너 DNS로 주소가 고정되고 레플리카도 설치 시점에 정해지므로 동적 디스커버리의 가치가 없고, L로 가도 k8s 디스커버리를 쓰지 Eureka를 쓰지 않는다. 학습 자산과 개발 편의를 위해 남긴 것이다.

**새 발견이 아니라 확인 항목이다.** 설치판을 실제로 뽑을 때 컨테이너·기동순서·하트비트 설명 비용을 다시 저울질한다.

## 4부. 검토 중 제기했다가 기각한 지적

> [!caution] 오탐 1건 — 권한 gRPC에 캐시·폴백이 없다는 지적
> 조사 초기에 "위키·ALM의 읽기 경로가 매번 org-service에 동기 gRPC로 물어보고 캐시나 폴백 흔적이 없다"고 적었다. **틀렸다.** 잘못된 디렉터리(`security/`, `grpc/`)를 grep한 결과였고, 실제 구현은 `permission/` 패키지에 있다.
>
> 실제 정책은 명시적으로 설계돼 있다. `GrpcPermissionClient`는 30초 Caffeine 캐시(최대 1만 엔트리)를 쓰고, 클래스 javadoc에 "권한 회수 반영 지연 30초 수용 — 스펙"이라고 근거까지 적혀 있다. 실패 처리도 갈라져 있다. UNAVAILABLE·DEADLINE_EXCEEDED는 503으로 전파하고([[20 프론트-백엔드 듀얼모드 연동 — 경계 매퍼·낙관적 락·503 전파 (2026-07-22)]]의 정책과 일치), 그 외 오류는 fail-closed로 거부한다. 가용성보다 인가 안전을 택한 의도적 선택이다. alm-backend도 같은 형태이고 deadline이 붙어 있다.
>
> 다만 org-service gRPC 서버에 인터셉터·서비스 인증·TLS가 없는 것은 **여전히 사실**이다. 이건 새 항목이 아니라 [[24 현재 아키텍처·구현 평가 + 개선 백로그 (2026-08-03)]]의 **M-04**가 이미 열어둔 건이다. 중복 등재하지 않는다.

## 유지해야 할 강점

- **서비스 경계가 도메인과 일치**한다. 따로 스케일하거나 끌 이유가 있는 단위로 잘려 있다.
- **논리 DB 분리 + Flyway**. 서비스가 남의 테이블을 보지 않아 물리 분리 시 코드가 안 바뀐다.
- **권한 원장 단일화**. 주체 원장은 org-service, 도메인 고유 제약은 각 서비스. 분리 축이 옳다.
- **인가 실패 정책이 명시적**이다. 캐시 수명, 503 전파, fail-closed가 코드와 주석에 근거까지 남아 있다.
- **계약을 proto로 명문화**했다. 갈라진 건 버전 관리이지 계약 자체가 아니다.
- 구조의 결 자체는 SaaS를 막지 않는다. 테넌트 축만 꽂으면 되는 모양은 갖췄다.

## 사용자 결정 대기

1. **온프렘 범위** — 인터넷 가능한 사내 서버 vs 완전 폐쇄망. O-01·O-02의 작업량이 갈린다.
2. **납품 형태** — 단일 고객 설치 vs 반복 납품 배포판.
3. **SaaS 여부** — 검토 중이라면 온프렘과 병행인지 대체인지. 병행이면 인스턴스 격리형으로 굳히고, 대체면 스키마 재설계를 정식 과제로 연다.
