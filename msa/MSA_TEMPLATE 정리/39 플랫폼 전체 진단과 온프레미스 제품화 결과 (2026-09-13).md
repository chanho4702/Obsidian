## 1. 한 장 요약

- **로그인이 실제로 막혀 있었다.** 런타임 Keycloak은 18080에 떠 있는데 auth-server가 코드 기본값 8080으로 리다이렉트했다. 공개 주소를 매개변수(`KC_PUBLIC_URL`/`KC_HOST_PORT`)로 빼고 auth에 같은 값을 배선한 뒤 auth만 재생성 → 302가 18080으로 가고 Keycloak 로그인 페이지 200(Codex도 직접 확인). 자격증명을 넣는 로그인 E2E는 하지 않았다.
- **하루 넘게 죽어 있던 컨테이너 4개**(Alloy·Grafana·Mailpit·collaboration 한 노드). 같은 밀리초에 exit 255 — 데몬/호스트 중단으로 *추정*할 뿐 증명은 없다. 원인이 무엇이든 `restart` 정책이 없어 안 돌아왔다. 상시 컨테이너 전부 `unless-stopped`로(소스 + 실행 중 컨테이너 `docker update`), 공동편집 2노드·로그 수집을 복구했다.
- **호스트 전 인터페이스에 열려 있던 것**(Postgres 5433·Redis 6379·S3Mock 19090·Grafana 3000, Grafana 익명 Admin)을 루프백·로그인 필수로 닫았다. LAN에서 실제로 닿는지는 호스트 방화벽에 달려 있고, 외부 침입이 증명된 것은 아니다.
- **데이터 손실 위험 둘**: 백업 스크립트가 실패해도 정상 백업을 지우던 것, ALM 저장 필터 이관이 재시도해야 할 4xx까지 영구 실패로 처리해 로컬 필터를 비우던 것. 둘 다 소스 수정 + 오프라인 회귀 테스트.
- **배포 신뢰성**(별개 문제): dispatch sha 대신 latest, `platform.env` 없어도 진행, TCP만 열리면 green. 소스 수정 + 테스트.
- **시크릿 노출**(별개 문제): smoke 실패 출력에 내부 토큰 값이 찍혔다. 상태만 출력하도록 수정.
- **잠복 결함**: `POSTGRES_PASSWORD`가 앱에 전달되지 않아 비밀번호를 바꾸는 순간 앱이 못 뜬다. 소스는 6개 앱 모두 고쳤고, 런타임은 auth만 적용(재생성됨) — 나머지 5개(board·org·wiki·alm·agent)는 앱 재생성 때 반영된다.
- **판정**: 검토한 수정 범위는 스펙 준수·코드 품질 모두 승인(Codex 최종). 도메인 경계·공통 인증·공유 아티팩트·설치 모드 스위치·dev 오프셋은 유지할 장점. 그러나 기본 자격증명, 공유 DB superuser, Keycloak 개발 모드(TLS 없음), 전체 복원 미검증, 서명/SBOM/CVE 미실시 때문에 **상용(고객 납품) 출시는 미승인**이다. 단일 서버 Compose 제품으로는 가깝고 HA는 별도 설계가 필요하다.

### 3-3. 아직 런타임에 없는 것 — 앱 재생성 때 반영

- **앱 코드 수정은 전부 소스에만 있다.** wiki-backend(검색 정렬)·alm-front(필터 이관)·wiki-front(언어 목록)·collaboration-service(Redis 기본값)·dev 프로필 Redis 포트는 새 이미지를 빌드하지도, 플릿에 배포하지도 않았다. 지금 실행 중인 컨테이너는 전부 기존 이미지 그대로다.
- **러너 역행 위험**: 다음 CI 배포가 **커밋되지 않은** 지금 compose가 아니라 커밋된 옛 compose를 쓰면 auth-server가 `KEYCLOAK_FRONT_ISSUER` 없이 재생성돼 로그인 리다이렉트가 다시 8080으로 돌아간다. 커밋·푸시 전에는 auth-server를 러너로 배포하지 않는다.
- `*_DB_PASSWORD`: board·org·wiki·alm·agent 5개(auth는 적용됨).
- 로그 JSON: compose env는 11개에 있으나 실제로 평문인 것은 eureka·board·org·wiki·docs 5개. gateway·alm·agent·migration·search는 앱 프로필로 이미 JSON이라 env 미적용이어도 결과가 같다.
- org의 `${VAR-1}` 의미, 위키 S3 매개변수(값 동일).
- 러너 배포는 **커밋 후**에만 새 compose·workflow를 쓴다. 다음 `up -d`에는 wiki·collab `--scale 2`가 필수다.

## 4. 온프레미스 출시 게이트 — 아직 못 넘은 것

아래는 이번에 **하지 않았거나 못 한 것**이다. 검토 범위 승인(§9)을 출시 승인으로 읽지 않는다.

1. **기본 자격증명**: DB 롤은 기본값이며 superuser·createdb·createrole이 전부 true(Codex SQL 확인). Keycloak admin·`start-dev`, MinIO, Grafana(볼륨에 남은 계정)도 기본값이다. 설치 시 기본 자격증명 교체를 강제하는 절차가 없다 — 운영 전 전부 교체해야 한다.
2. **TLS·호스트명**: Keycloak은 개발 모드·http다. 역프록시 뒤 운영 구성은 문서에 규칙(직접 게시 vs 역프록시)만 있고 구현·검증은 없다. — [Keycloak production](https://www.keycloak.org/server/configuration-production) · [reverse proxy](https://www.keycloak.org/server/reverseproxy)
3. **전체 백업·복원**: 스크립트는 ALM(almdb + MinIO 버킷)만이고 `pg_restore --list`는 TOC 확인이지 복원 검증이 아니다. 앱 DB 9개 + 위키 첨부(S3Mock 에뮬레이터) + MinIO + auth JWK + 메일/암호화 키 + 구성의 전체 복원 리허설이 없다. — [PostgreSQL 16 backup](https://www.postgresql.org/docs/16/backup.html) · [continuous archiving](https://www.postgresql.org/docs/16/continuous-archiving.html)
4. **공급망**: 이미지 서명·SBOM·CVE 스캔·라이선스 판정 미실시. — [cosign verify](https://docs.sigstore.dev/cosign/verifying/verify/)
5. **런타임 지원 기간**: 이미지가 Temurin 24인데 JDK 24 지원은 2025-09 종료. LTS 25 전환은 호환성 검증 뒤 출시 게이트로 둔다(이번에 임의 변경하지 않음). — [Adoptium support](https://adoptium.net/support)
6. **용량**: 실행 중 20개 컨테이너 합 약 10.97GiB(검색 ON, 4개 다운 시점, 부하 시험 아님), Docker VM 한도 14.56GiB. 출시 최소 사양·동접 수는 인증치가 아니고 컨테이너 리소스 제한도 기본 무제한. — [resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)
7. **패키징**: 멀티리포 릴리스 매니페스트·호환성 매트릭스, 오프라인 설치 패키지(이미지 save + dist + 서명 + 설정 스키마 + 프리플라이트 + 복원 검증)가 없다. — [docker image save](https://docs.docker.com/reference/cli/docker/image/save/)
8. **위키 첨부 저장소**: 배포본이 S3Mock(에뮬레이터, 운영 금지 명시)을 쓴다. MinIO 전환은 이제 env로 가능하지만 데이터 이전 절차는 문서 한 줄뿐이다.
9. **프론트 번들**: ALM main 1895.54KB(gzip 578.61KB), 포털 2111.09KB(gzip 645.07KB) — route 단위 lazy 개선은 향후 검증 과제.

## 5. 아키텍처 판정과 조언

### 5-1. 실제 구조(재확인)

- 프론트: 소스 SPA 3개(myFront 포털·wiki·alm) + docs 빌드(wiki-front `--mode docs`). nginx :80이 정적 서빙 + `/api|/oauth2|/login|/.well-known`을 게이트웨이로 프록시. `/api/docs`만 의도된 공개 read-only 직결 예외.
- 백엔드: **배포 서비스 12개 / 리포 10개**(collaboration은 Node, org·search는 platform-backend 한 리포, wiki·docs는 같은 이미지). wiki·board 등은 유레카 lb, org·search·agent·migration은 컨테이너 DNS 직결(설계 결정).
- 데이터: Postgres 물리 1개에 앱 DB 9개(한 롤 공유 — 권한 격리도 HA도 아님), Redis 1개(prod DB0·dev DB1 같은 프로세스), 이벤트는 Redis Streams(afterCommit 발행 실패 시 재색인으로 복구 — 기존 트레이드오프, Kafka 전환 제안하지 않음), 객체 저장소는 ALM/org MinIO·wiki S3Mock, auth JWK는 `platform-auth-jwk` 볼륨의 `/data/auth-jwk.json`에 영속.
- 에이전트: Dispatcher는 기본 OFF. 워커가 환경을 상속하는 구조는 제약 조건으로 적고 새 취약점으로 단정하지 않는다.

### 5-2. 유지할 장점

도메인 경계(위키/ALM/org/검색/이관/에이전트), 공통 인증(Keycloak 리다이렉트 + 게이트웨이 PAT 교환 + `common-starter` JWT 검증), 공유 아티팩트 단일 버전(`common-proto`/`common-starter`), 설치 옵션 모드 스위치(`MAIL_MODE`/`SEARCH_MODE`), dev 오프셋(+10000) 공존. 이번에 하나도 되돌리지 않았다(확정 설계 결정 보존).

### 5-3. 현실적인 조언

- **Single Server(Compose) 우선**: 지금 구조의 자연스러운 제품 형태다. 호스트가 하나라 wiki·collab 2노드는 부하 분산이지 HA가 아니다. 출시 전 순서: 기본 자격증명 교체 강제 → KC 운영 모드(TLS/호스트명, 역프록시) → 전체 백업·복원 리허설 → 서명/SBOM/CVE → 릴리스 매니페스트. 운영 오버레이는 [Compose in production](https://docs.docker.com/compose/how-tos/production/) 방식으로 dev 기본값과 분리한다.
- **HA 고객만**: Postgres·Redis·객체 저장소·Keycloak을 각각 별도 실패 영역(관리형 또는 복제)으로 빼는 설계가 먼저다. 앱 레플리카만 늘려서는 HA가 되지 않는다.
- **오프라인 설치**: 이미지 `docker save` 묶음 + 프론트 dist + 서명 + 설정 스키마 + 프리플라이트(포트 예약 구간·기존 Redis 같은 호스트 충돌 검사) + 복원 검증 스크립트를 한 패키지로. 이번에 만든 `smoke-stack.ps1 -ConfigOnly`·`dev-up-local` 프리플라이트·헬스 게이트가 그 씨앗이다.
- **포트 게시 원칙**: 브라우저가 직접 닿아야 하는 것(nginx 80, Keycloak 공개 포트)만 전 인터페이스, 나머지는 루프백 또는 미게시. — [port publishing](https://docs.docker.com/engine/network/port-publishing/)
- **출시 전 짧은 체크리스트**(이번에 하지 않은 것):
  - DB는 서비스별 롤로 최소 권한 분리(앱 롤은 자기 DB만, superuser 아님), Flyway 마이그레이션은 별도 마이그레이션 롤로.
  - 복원 증명: RPO(허용 손실 시간)·RTO(복구 시간)를 정하고 실제 복원 리허설로 측정한 값을 문서에 남긴다.
  - 알림: 서비스 SLO(가용성·지연), 이벤트 스트림 소비 지연(`XPENDING`·DLQ 길이), 백업 나이(마지막 성공 후 경과)에 경보를 건다.
  - 오프라인 설치의 한계를 미리 알린다: 구글 로그인, 외부 SMTP, 외부 OpenSearch(`SEARCH_MODE=external`)는 망 연결이 있어야 동작한다.
  - 스키마 변경은 확장→전환→축소(expand-contract) 순서로 해 롤백 이미지가 옛 스키마에서도 돌게 한다. 되돌리기 어려운 변경(컬럼 삭제·NOT NULL)은 백필과 함께.

- **종합**: 검토한 수정 범위는 승인(Codex 최종 판정과 일치). **온프렘 상용 출시는 미승인** — §4 게이트를 넘겨야 하며, 운영 플릿 미배포(§3-3)와 커밋 여부는 사용자 결정이다.
