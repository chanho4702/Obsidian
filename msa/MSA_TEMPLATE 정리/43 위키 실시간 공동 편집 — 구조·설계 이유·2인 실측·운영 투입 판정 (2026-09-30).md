## 1. 구성 — 누가 무엇을 하나

> [!note] 배경지식 — CRDT와 Yjs
> 두 사람이 같은 줄을 동시에 고치면 "누구 걸 살리나"를 정해야 한다. **CRDT**는 모든 편집을 순서와 무관하게 똑같은 결과로 합쳐지는 형태로 저장하는 자료구조다. 서버에 먼저 물어보지 않아도 각자 합치면 결과가 같아진다. **Yjs**는 그 구현체이고, 오프라인 중 편집도 다시 연결되면 자동으로 합쳐진다.

```text
브라우저(wiki-front, TipTap 에디터 + Yjs)
   │ ① JWT REST: 입장권 주세요                     ┌──────────── Redis ─────────────┐
   ├──────────────▶ wiki-backend ── EDIT 권한 확인 ─▶│ 1회용 입장권 (1분, 해시 키)      │
   │                                               │ 노드 간 변경·커서 중계(pub/sub) │
   │ ② 입장권으로 최초 문서 넣기(bootstrap, HTTP)    │ 저장 락                         │
   ├──────────────▶ collaboration-service ──GETDEL─▶└────────────────────────────────┘
   │ ③ 입장권으로 웹소켓 접속                              │
   └══════════════▶ collaboration-service ────────▶ PostgreSQL wikidb.collaboration_document (Yjs 바이너리 정본)
   │ ④ 게시: 공동 초안 → 페이지 리비전(단일 트랜잭션)
   └──────────────▶ wiki-backend ── page + collaboration_document 행 잠금 → 리비전 생성
```

경로는 모두 `nginx → gateway → 서비스`다. nginx는 `/api/wiki/collaboration`에 웹소켓 업그레이드와 1시간 타임아웃을 건다(`infra/nginx/default.conf:55`). 게이트웨이는 bootstrap(HTTP)과 WS를 각각 `COLLABORATION_SERVICE_HTTP_URI`와 `COLLABORATION_SERVICE_URI`로 보낸다. 이 경로는 JWT 없이 열려 있고, **입장권이 유일한 인증**이다.

### 1-1. 단계별 흐름

1. **입장권 발급** (`wiki-backend` `CollaborationTicketService.issue`)
   - 편집 권한(스페이스 EDIT와 페이지 제한)을 확인한다.
   - 32바이트 무작위 값을 만들고, Redis 키 `wiki:collaboration:ticket:v1:<sha256>`에 8개 필드짜리 내용을 TTL 1분으로 저장한다.
   - Redis가 죽어 있으면 503이다.
2. **최초 문서 넣기** (bootstrap)
   - 브라우저가 현재 Markdown과 제목으로 Yjs 문서를 만들어 한 번 올린다.
   - 서버는 `INSERT … ON CONFLICT DO NOTHING`으로 **처음 한 명만** 넣는다. 나머지는 이미 있는 초안을 받는다. 이렇게 두 사람이 동시에 처음 들어와도 내용이 두 번 들어가지 않는다.
   - bootstrap 행이 없는 방은 웹소켓 로드도 거부한다.
3. **웹소켓 세션**
   - 새 입장권으로 방 `page:<id>`에 들어간다. 재연결할 때마다 입장권을 새로 받는다.
   - 커서와 이름(awareness)은 서버가 입장권의 신원으로 **덮어쓴다.** 남의 이름으로 위장하거나 남의 커서를 움직일 수 없다.
4. **저장**
   - 변경은 2초 debounce(최대 10초)로 PostgreSQL `bytea`에 통째로 저장된다.
   - 노드가 여러 대면 Redis 락을 잡은 노드만 저장한다.
5. **게시** (`PUT /api/wiki/pages/{id}/collaboration-draft`)
   - page 행과 초안 행을 `FOR UPDATE`로 잠근다.
   - 버전과 세대(generation)가 기대값과 같을 때만 리비전을 만들고 세대를 +1 한다.
   - 공동 초안은 게시 뒤에도 이어진다. 게시는 "현재 공동 초안을 정본 리비전으로 찍는 것"이다.
   - 프론트는 상태가 `synced`일 때만 게시 버튼을 연다(`availability.ts`).

## 2. 왜 이렇게 만들었나

`collaboration-service/CLAUDE.md`의 "되돌리지 말 것" 7개 항목이 결정의 기록이다. 다만 **이유는 문서에 없고**, 아래는 코드와 문맥으로 재구성한 것이다.

| 결정 | 이유(재구성) |
|---|---|
| 위키 서버와 **분리된 Node 서비스** | Spring REST는 짧은 요청·응답에 맞춰져 있다. 웹소켓은 사람마다 연결을 몇 시간씩 잡고 있다. 섞으면 편집 인원이 조회 성능을 잡아먹는다. Yjs·Hocuspocus 생태계가 JS라서 Node를 골랐다 |
| **Yjs + 셀프호스팅 Hocuspocus** | 동시 편집 병합은 직접 짜기 가장 어려운 부분이라 검증된 CRDT를 쓴다. TipTap과 바로 붙는다. 외부 SaaS가 아니라서 **온프렘 설치판**에 넣을 수 있다 |
| **1회용 입장권**(Access Token을 WS로 안 보냄) | 웹소켓은 인증을 URL에 싣기 쉽고, URL은 로그에 남는다. 권한 판단은 원래 하던 wiki-backend에 두고, 새어도 이미 쓴 1분짜리 표만 넘긴다 |
| awareness를 **서버가 재작성** | 클라이언트가 보낸 이름과 색은 믿을 수 없다(사칭 방지) |
| **PostgreSQL 정본 + Redis 중계** | 둘 다 플랫폼에 이미 있다(확정 결정: DB는 PostgreSQL 통일). 영구 보관은 PG, 잠깐 쓰고 버리는 노드 간 전달과 커서는 Redis가 맡는다 |
| 로그는 **stdout JSON** | 확정 결정(Alloy → Loki → Grafana). 입장권 원문과 문서 본문은 로그에 남기지 않는다 |
| 플래그를 **기본 꺼둠** | 문서가 깨지면 되돌리기 어려운 기능이라 단계적으로 켠다. README 기준 남은 관문은 "2인 브라우저 caret UX 실측" 하나였다(이번에 수행) |

## 3. 2인 실측 (2026-09-30)

### 3-1. 방법 — 운영 배포본은 건드리지 않았다

- 플래그를 켠 wiki-front를 **임시 폴더에 따로 빌드**했다(`VITE_WIKI_COLLABORATION_ENABLED=true vite build --outDir <scratch>`).
- Playwright(시스템 Chrome)로 `http://localhost/wiki/**` 요청만 그 빌드로 바꿔 서빙했다. API와 WS는 실제 nginx → 게이트웨이 → 도커 스택으로 갔다.
- 사용자는 realm `sso-demo`의 `alice/alice`와 `admin/admin`이다. admin은 테스트 스페이스(id 1) 권한이 없어서, 테스트 동안만 EDITOR grant를 주고 끝나면 회수했다.
- 테스트 페이지(67~72)는 끝난 뒤 휴지통으로 옮겼다.

> [!warning] 재현할 때 걸리는 함정 3개
> 1. Playwright가 문서를 대신 서빙하면 Chrome이 그 문서를 "주소 모름"으로 보고 `ws://localhost`를 **로컬 네트워크 접근 차단**(`ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`)한다. 테스트 도구 때문에 생기는 문제이고, 실제 nginx 같은 출처에서는 안 생긴다. `--disable-features=LocalNetworkAccessChecks,LocalNetworkAccessChecksWebSockets`로 끈다.
> 2. OIDC 로그인 뒤 리다이렉트 응답은 route 가로채기를 타지 않아서 운영 번들이 섞인다. 로그인 뒤 `/wiki/`로 한 번 더 이동해야 한다.
> 3. grant 직후 몇 초는 권한 캐시 때문에 입장권 발급이 403이다. 페이지 GET이 200이 될 때까지 기다린다.

## 6. 결함 목록

검증 표기: **실측** = 이번에 브라우저로 재현 / **코드** = 코드로 확인 / **추정** = 코드 경로만 확인, 발생은 추정

### 차단 (켜기 전 필수)

**차단-1. 다른 경로로 저장하면 그 페이지는 공동 편집으로 영영 안 열린다** — 실측
- 일반 저장 PUT, 리비전 복원, 이관 임포트, agent-service 쓰기가 페이지 버전을 올린다. 그런데 `collaboration_document.base_page_version`은 그대로 남는다.
- 그 뒤 bootstrap은 옛 기준을 돌려주고, 프론트는 "공동 초안은 페이지 vN을 기준으로 합니다"로 멈춘다. 게시 API도 항상 409다.
- 복구 수단은 DB 행 삭제뿐이다.
- 플래그를 껐다가 다시 켜도 같은 일이 생긴다. 꺼져 있던 동안 저장된 모든 페이지가 잠긴다.
- **고칠 방향:** 버전을 올리는 모든 쓰기에서 같은 트랜잭션 안에 초안 행을 잠그고 무효화(삭제 또는 세대 +1)한다. 열린 세션을 끊는 신호와 관리자용 초안 초기화 API도 둔다.

**차단-2. 게이트웨이 웹소켓 프레임 상한 64KB** — 실측
- `spring.cloud.gateway.httpclient.websocket.max-frame-payload-length`가 설정돼 있지 않다. reactor-netty 기본값은 65536이다.
- Yjs 상태가 64KB를 넘는 문서는 첫 동기화에서 끊기고 무한 재연결에 빠진다. 큰 붙여넣기도 같다.
- 지금까지 한 "nginx 경로 실측"은 표 2행짜리 작은 문서였다.
- **고칠 방향:** 상한을 `MAX_DOCUMENT_BYTES`(10MB) 이상으로 설정하고, 게이트웨이 경유 대형 문서 E2E를 추가한다.

### 높음

**높음-1. 권한 회수·삭제·이동이 열린 세션에 반영되지 않는다** — 코드
- 인증은 접속할 때 한 번뿐이다. 권한을 뺏긴 사람도 연결이 끊길 때까지 계속 읽고 쓴다(읽기 유출).
- 휴지통으로 보낸 페이지도 게시만 막히고 편집은 계속된다.

**높음-2. 다른 노드에서 온 커서·참여자 정보가 모두 버려진다** — 코드
- Redis로 들어온 awareness에는 연결 context가 없다. 그래서 `applyAuthoritativeAwareness`가 `MISSING_CONTEXT`로 비워 버린다.
- 2노드에서는 다른 노드 사람이 안 보이고 warn 로그가 쏟아진다.
- 지금은 위 관찰대로 한 노드만 쓰여서 드러나지 않았을 가능성이 있다.

**높음-3. 다중 노드 저장이 전체 상태 덮어쓰기라, 뒤처진 노드가 앞선 편집을 지울 수 있다** — 추정
- Redis 순단 중 publish가 실패하면 조용히 삼킨다. 락 경합으로 마지막 저장을 건너뛴 채 언로드되는 경로도 있다.
- **고칠 방향:** 저장할 때 DB 상태와 `Y.mergeUpdates`로 병합해 단조 저장한다.

**높음-4. 10MB 상한을 넘은 문서는 조용히 영구 미저장** — 코드
- 저장이 실패해도 클라이언트는 계속 `synced`를 보여 준다. 재기동하면 유실된다.

**높음-5. 네트워크 복귀 뒤 "재연결 중" 고착 → 게시 불가** — 실측(이번에 새로 발견)
- `useCollaborationSession.ts:67`의 `online` 핸들러가 상태를 `reconnecting`으로 바꾼다.
- 그런데 실제 웹소켓은 살아 있어서 provider가 새 상태 이벤트를 내지 않는다. 그래서 라벨이 영원히 "재연결 중"이다.
- 데이터는 양방향으로 잘 오가지만 게시 버튼이 `synced`가 아니라서 막힌다. 새로고침해야 풀린다.
- 와이파이 순단 같은 흔한 상황에서 일어난다.
- **고칠 방향:** `online`에서 상태를 강제하지 말고 provider 상태를 다시 읽는다. 연결이 이미 synced면 synced로 되돌리고, 아니면 `provider.connect()`를 호출한다.

### 중간

- **보관된 페이지 우회:** 보관된 페이지도 공동 편집으로는 수정·게시된다. 일반 저장은 409로 막는데 게시 경로에는 그 검사가 없다.
- **영구 삭제 뒤 본문 잔존:** 영구 삭제한 페이지 본문이 `collaboration_document`에 남는다. FK도 정리 코드도 없어서 보존·개인정보 문제가 된다.
- **"서버 최신본으로 다시 불러오기" 무효:** 공동 모드에서는 실제로 아무것도 버리지 않는다. 확인창 문구와 동작이 다르다.
- **nginx 본문 1MB:** `client_max_body_size`가 기본 1MB라 bootstrap과 게시가 서비스 상한(10MB)보다 먼저 HTML 413으로 막힌다.
- **일반 저장 행 잠금 없음:** 게시와 경쟁하면 같은 버전 리비전이 두 개 생길 수 있다(추정).
- **테스트 공백:** 자동 테스트가 배선, 다중 노드, 권한 회수, 크기 상한을 다루지 않는다.

### 낮음

- 공동 모드 게시는 변경 요약을 보내지 않는다. 입력란은 보이는데 입력값은 버려진다.
- 제목을 비운 채 재동기화되면 "제목 형식이 오래되었습니다"로 막힌다. 안내 문구에 나오는 "초안 재설정" 기능은 없다.
- 기준 불일치 오류 뒤 "다시 연결"을 누르면 같은 오류가 반복된다.
- compose에 `stop_grace_period`가 없다. 기본 10초가 `SHUTDOWN_TIMEOUT_MS`와 같아서 종료 여유가 없다.

### 잘 된 점 (반증을 시도했지만 결함 없음)

- 입장권 1회 소비(GETDEL), 해시 키, 원문 미로그, room·스키마·만료 재검증, Redis 장애 시 거부(fail-closed).
- bootstrap에서 본문을 받기 전에 인증, 손상된 update 거부(422), 중복 seed 차단.
- 같은 세대 동시 게시는 행 잠금으로 하나만 성공.
- 같은 노드 안의 사칭과 clientId 탈취 차단. 확정 설계 결정(common-starter, 로그 경로 등)과 충돌 없음.

## 7. 켜기까지의 순서

1. 차단-1과 차단-2를 고친다(wiki-backend 쓰기 경로 + 초안 무효화, gateway 프레임 상한).
2. 높음-5(재연결 고착)를 고친다. 프론트만 고치면 되는 작은 수정이다.
3. 높음-1~4를 고친다(권한 재검증, 원격 awareness 통과, 병합 저장, 상한 초과 알림). 게이트웨이의 노드 분산도 확인한다.
4. 자동 E2E를 추가한다. 게이트웨이 경유 대형 문서, 2노드 커서·저장, 다른 경로 저장 후 편집, 오프라인 복귀 후 게시.
5. 스테이징에서 `VITE_WIKI_COLLABORATION_ENABLED=true`로 빌드해 재검증한 뒤 운영 CI 빌드 env에 넣는다.

**켜는 법(참고):** wiki-front 빌드 시 `VITE_WIKI_COLLABORATION_ENABLED=true`. 빌드 시점 상수라 재빌드와 배포가 필요하다. 서버 쪽은 이미 떠 있다.

### 설계에서 배운 것
- **초안 행을 지우면 안 된다.** 저장이 upsert라서 메모리의 옛 문서가 행을 되살린다. 그래서 행을 "제자리 리셋"하고 번호로 막는다.
- **`generation`과 `reset_epoch`를 분리한다.** 첫 명세는 저장 가드를 generation으로 잡았는데, 정상 게시도 generation을 올린다. 그래서 게시 한 번이면 남은 편집자가 쫓겨나고, 게시 직전 편집이 초안에서 빠졌다(리뷰 C-1). 리셋에서만 오르는 `reset_epoch`를 따로 두어 해결했다. 저장 가드에 generation을 쓰지 않는다는 원칙을 collaboration-service `CLAUDE.md`에 적었다.
- **재연결은 epoch로만 판정한다.** 정상 게시로 pageVersion이 오른 뒤 재연결을 리셋으로 오판하던 문제가 있었다.
- **공동 모드 게시 본문은 항상 공유 문서다.** dirty 판정으로 `initialBody`를 보내면 최신 게시본을 덮는다(43번 §6 낮음의 "dirty 판정"이 실제로 재현됐다).

### 검증
- **게이트:** collaboration-service 123, wiki-backend 510, gateway 176, wiki-front 1243 테스트 모두 통과.
- **리뷰:** 리뷰 에이전트 2회. 1차는 C-1 반려, 2차는 머지 가능.
- **Codex 교차검증:** 5회. 병렬 실행은 Windows 샌드박스 오류(1909)로 실패했고, 순차 실행으로 바꾼 뒤 정상 동작했다. 매회 재현된 결함을 반영했고, 최종은 collaboration-service 결함 없음, wiki-front 1건(로컬 사본 미저장 경고)을 반영했다.
- **실측 E2E 14/14(배포 이미지 기준):** 2인 접속·수렴, 오프라인 복귀 후 게시 가능, 게시 뒤 상대 편집 유지와 게시 직전 편집 보존, 게시 뒤 협업 서버 재시작 재연결 오탐 없음, 편집 중 일반 저장 → 양쪽 리셋 패널 → 최신본 기준 재시작(중복 없음), 200KB 문서 연결·저장.

### 남은 것 (플래그를 켜기 전)
- **높음-1:** 권한 회수, 삭제, 이동이 열린 세션에 반영되지 않는다.
- **높음-2:** 다른 노드의 awareness가 버려진다. 채널을 epoch로 격리한 뒤 재확인이 필요하다.
- **높음-3:** Redis 순단 중 노드 간 전체 상태 덮어쓰기. 리셋 경로는 격리됐지만 평상시 순단 경로는 남아 있다.
- **높음-4:** 10MB 초과 시 조용히 미저장된다.
- **중간 항목 전부:** 보관 페이지 우회, purge 후 잔존, 변경 요약 누락 등.
- **게이트웨이가 한 노드에만 붙는 문제.**
- **UX 문구:** 정상 게시로 생긴 409도 리셋 패널 제목("다른 경로의 저장으로…")으로 뜬다. 데이터는 안전하다.
- **E2E 스크립트 자산화:** 이번 E2E는 세션 임시 폴더의 Playwright 스크립트였다. 리포 자동 E2E로 옮기는 것은 §7-4로 남는다.
