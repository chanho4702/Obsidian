# 34. 위키 컨플루언스 파리티 W21 + 규모 대응 — 휴지통·라벨·첨부·인라인댓글·지연트리 (2026-08-29)

> 시작은 "컨플루언스랑 기능요구사항 비교해서 없는 것·미흡한 것 반영해줘".
> 갭 분석 → 상위 4묶음 구현 → "2테라도 버티냐" 질문 → 규모 대응까지 이어진 세션.
> 결과: wiki-backend 220 테스트 · wiki-front 813 테스트 + typecheck + production build 그린.
> 브랜치 `feat/w21-parity-and-scale` 양쪽 리포에 1커밋씩(푸시 전).
> 정본 문서: `wiki-front/docs/roadmap/2026-08-28-confluence-feature-parity.md`

## 1. 무엇이 문제였나 — 갭 분석의 결론

에디터·실시간 공동 편집·페이지 제한은 이미 컨플루언스 수준이었다.
**남은 격차는 문서를 쓰는 기능이 아니라 문서를 관리하는 기능**에 몰려 있었다.

| 없던 것 | 실제 증상 |
|---|---|
| 휴지통 | 삭제가 hard delete — 첨부·리비전·댓글까지 즉시 사라지고 되돌릴 수 없다 |
| 라벨·백링크 | 문서가 수백 건이 되면 트리만으로는 못 찾는다 |
| 첨부파일 화면 | `listAttachments`를 부르는 UI가 없어 **이미지 말고는 파일을 올릴 방법이 없었다** |
| 내보내기 | 내용을 밖으로 꺼낼 경로가 전무 — 도구 교체·감사 대응 시 탈출구 없음 |
| 인라인 댓글·구독 | 페이지 댓글만으로는 "이 문장"을 가리킬 수 없고, 알림을 끌 수도 없었다 |

미흡했던 것: 복제가 하위·권한을 안 옮김, 즐겨찾기·최근 방문이 브라우저 로컬에만 저장,
검색 필터가 스페이스·타입뿐, 버전 비교가 직전 버전 고정.

## 2. W21 — 네 묶음, 그리고 그때 내린 판단

### 2-1. 휴지통 (V13)

- 삭제를 소프트 삭제로. **Page 엔티티에 `@SQLRestriction("deleted_at is null")`** 을 걸어
  모든 JPQL·파생 쿼리에서 자동으로 빠지게 했다.
  → 조회 경로마다 손으로 `deleted_at is null`을 붙이는 방식은 한 군데만 빠뜨려도
  버린 문서가 트리·검색·첨부 어딘가에서 되살아난다. 휴지통을 읽는 우회는
  `PageRepository`의 네이티브 쿼리 한 곳으로 몰아 "어디서 되살아날 수 있는가"를 한 곳에서 감사한다.
- `deleted_root`로 복원 묶음의 경계를 잡는다. cascade로 딸려간 자손은 함께 복원되지만,
  **따로 먼저 버려둔 하위 묶음은 상위 복원에 휩쓸리지 않는다**(사용자의 두 결정을 각각 지킨다).
- 부모가 사라진 뒤 복원하면 최상위로 올리고 그 사실을 화면이 알린다 — 안 그러면 문서가
  트리 어디에도 없는 고아가 된다.
- 영구 삭제·비우기는 스페이스 ADMIN. 삭제 권한과 영구 삭제 권한을 분리하는 것이 휴지통의 요점이다.

**실측 함정 2개**
- `@SQLRestriction`은 **JPQL 대량 삭제(`deleteAllInBatch`)에도 걸린다** → 영구 삭제가 0행.
  네이티브 delete로 바꿔야 한다.
- 제한 인덱스가 `findIdParentBySpaceId`(JPQL)를 쓰고 있어 버려진 페이지가 조상 체인에서 빠졌다.
  → 제한된 부모 밑에서 버려진 문서를 아무나 휴지통에서 볼 수 있는 **누출**. 네이티브로 바꿔 해소.
  `PageRestriction.findBySpaceId`의 JPQL 서브쿼리도 같은 이유로 네이티브 전환.

### 2-2. 라벨·백링크 (V14)

- 라벨 이름 정규화: trim + 소문자 + 내부 공백은 하이픈. "Design"과 "design"이 갈리면
  목록이 금세 무의미해진다.
- **백링크 대상은 페이지 id가 아니라 제목이다.** 이 위키의 `[[제목]]`은 렌더 시점에 같은
  스페이스의 제목으로 해석되므로, 저장된 그래프도 같은 기준이어야 화면과 어긋나지 않는다.
  링크 그래프는 본문의 파생물이라 저장할 때마다 전량 재작성한다.
- 코드 펜스·인라인 코드 안의 대괄호는 링크로 세지 않는다(렌더러와 같은 규칙).

### 2-3. 첨부 화면 + 내보내기

- **백엔드는 변경 없음.** 실측해보니 기본 업로드가 이미 `CONFIRMED`로 저장되고 있었다 —
  없던 것은 화면뿐이었다. (`confirm`이 "본문 참조"를 요구하는 것은 에디터 PENDING 경로 한정)
- 내보내기는 Markdown(저장 형식 그대로라 무손실)과 HTML(이미지를 data URI로 심어 자기완결).
  **HTML은 보기 화면과 같은 렌더러(MarkdownView)를 `renderToStaticMarkup`으로 돌린다** —
  별도 변환 파이프라인을 두면 확장 문법(패널·컬럼·표 병합)에서 화면과 결과가 갈린다.
  `react-dom/server`는 동적 import라 이 기능을 쓸 때만 번들을 받는다(별도 청크 189KB).
- **PDF는 브라우저 인쇄로 넘겼다.** 자체 렌더러 없이 만든 PDF는 표·코드 블록이 화면과
  어긋나 오히려 신뢰를 깎는다.

### 2-4. 인라인 댓글 + 구독 (V15)

- **앵커는 렌더된 본문의 인용문 + 등장 순번이다.** 처음엔 서버가 마크다운 원문과 대조하게
  만들었다가 되돌렸다 — 서식을 가로지르는 선택(`배포는 **금요일**에`)은 원문에 그대로 없어
  **정당한 선택까지 거부**한다. 서버는 앵커를 보관만 하고 위치 찾기는 렌더러가 한다.
  저장 형식이 마크다운 문자열이라 안정적인 블록 id가 없다는 사실의 직접적 귀결.
- 본문이 바뀌어 인용을 못 찾으면 스레드를 지우지 않고 "위치 없음"으로 남긴다.
  대화가 편집 한 번에 사라지는 쪽이 훨씬 나쁘다.
- **알림 대상 모델을 교체했다.** "작성자 + 리비전을 남긴 편집자"는 코드에 박힌 계산식이라
  끌 수가 없었다(한 번 고친 문서의 알림을 영영 받는다). `page_watch`를 단일 원장으로 두고,
  기존 사용자는 마이그레이션 백필로 승계. 프론트 목업도 `normalize`에서 같은 백필을 한다.

## 3. "2테라면 버티나" — 규모 대응

용량 자체는 문제가 아니었다. 2TB는 사실상 전부 첨부파일이고 그건 S3로 빠진다.
**먼저 무너지는 곳은 요청당 비용이 스페이스 크기에 비례하는 지점**이었다.

### 3-1. 권한 판정 — 해결

문제: 제한 판정이 요청마다 `findIdParentAnyBySpaceId`로 **스페이스 전 페이지**를 읽어
부모 맵을 만들었다. 페이지 한 장 여는 비용이 스페이스 크기에 비례.

해결: 대상의 **조상 폐포만** 읽는다(재귀 CTE 1쿼리 + 그 id들의 제한 행).
스페이스 전량이 정말 필요한 곳은 트리 필터(`visiblePageIds`) 하나뿐이라 거기만 남겼다.

> **캐시를 얹지 않은 것은 의도다.** 제한·트리 변경 직후의 스테일 인덱스는 그대로 누출이라,
> 무효화가 완벽해야만 안전한 캐시보다 질의를 싸게 만드는 쪽을 택했다.
> (다중 노드에서 무효화가 늦는 창을 감수해야 하는데, 그 창이 곧 권한 우회다)

회귀 가드: `PermissionQueryScaleTest` — Hibernate statistics로 5페이지 스페이스와
300페이지 스페이스의 조회 질의 수가 **같아야** 통과.

### 3-2. 리비전 보존 — 정책 결정 후 해결

문제: 저장할 때마다 본문 전체가 새 리비전으로 복사된다. 1MB 문서를 백 번 고치면 100MB.
휴지통 도입으로 지운 문서의 이력까지 남아 증가 속도가 더 빨라졌다.

정책(사용자 결정): **전부 보관 + 압축만**. 이력 손실 없음.

해결(V16): gzip 압축본을 BYTEA에 담고 `STORAGE EXTERNAL`로 TOAST의 이중 압축을 막았다.
Postgres가 큰 TEXT를 이미 한 번 누르지만 비율이 낮고 2KB 미만은 아예 압축하지 않는다.
512자 미만은 gzip 헤더(18B) 때문에 오히려 커져 평문으로 둔다.
기존 행은 그대로 두고 엔티티가 둘 중 있는 쪽을 읽으므로 일괄 변환이 필요 없다.

### 3-3. 트리·전체목록 지연 로딩 — 진행 중(전면 리팩터 선택)

문제: 프론트가 스페이스 전 페이지를 한 번에 받아 트리·`[[링크]]` 해석·자동완성·
브레드크럼을 **그 배열 하나로** 처리했다. 20개 파일이 이 목록에 의존.

**순서가 핵심이다.** 트리를 지연 로딩으로 뒤집는 순간 컨텍스트의 `pages`는 "전부"가 아니라
"지금까지 로드한 것"이 된다. 완전한 목록을 전제하던 소비처가 그대로면 **조용히 틀린 결과**를
낸다(없는 링크로 표시, 자식 누락). 그래서 소비처를 먼저 옮기고 트리를 마지막에 뒤집는다.

끝난 것 — 백엔드 API 5종(전부 effective VIEW 필터 + 누출 테스트):
직계 자식(`childCount` 포함) · 조상 체인 · 후손 폐포 · 제목 정확 조회 · 제목 부분 검색.

> `childCount`가 필요한 이유: 지연 트리는 자식을 불러오기 **전에** 펼침 화살표를 그릴지
> 정해야 한다. 없으면 "펼쳤더니 비어 있는" 노드가 생기거나, 화살표를 그리려고 전부 미리 불러온다.

끝난 것 — 프론트 소비처 이관:

| 소비처 | 이전 | 지금 |
|---|---|---|
| `[[제목]]` 해석 | 전 페이지에서 제목 색인 | 본문에 등장한 제목만 조회 |
| `[[` 자동완성 | 전 페이지 필터 | 서버 제목 검색(빈 질의 = 최상위 문서) |
| 링크 칩 존재/부재 | 전 페이지 | 문서 등장 제목의 조회 결과 캐시 |
| 붙여넣기 링크 메뉴 | 전 페이지에서 id 조회 | URL에서 id만, 제목은 서버 |
| 공동 편집 세션 | 전 페이지 배열 보유 | 편집 화면과 같은 링크 캐시 공유 |
| 하위 페이지 목록 | 전 페이지 필터 | 직계 자식 조회 |
| 내보내기(하위 포함) | 전 페이지로 서브트리 계산 | 후손 폐포 + 클라이언트 정렬 |

**실측 함정**: tiptap `@tiptap/suggestion`의 `items()`는 동기 결과를 기대한다. 비동기 조회
결과가 `onStart`보다 **먼저** 도착하는 경우가 실제로 있었다(목업 스토어). 그래서
`onStart`/`onUpdate`에서 `props.items`를 믿지 않고 **항상 캐시로 다시 계산**하고,
늦게 온 결과는 `registerRefresh`로 플러그인 내부 items까지 갱신해야 Enter·화살표가 동작한다.

남은 것: 사이드바 트리 자체(`PageTree`·`GlobalSidebar`·`AppShell` 컨텍스트),
`SpaceIndexPage`, 이동 대상 선택기.

## 4. 되돌리지 말 것

- 인라인 앵커를 마크다운 원문 오프셋으로 — 서식을 가로지르는 선택을 표현 못 한다.
- 알림 대상을 "작성자+편집자" 계산식으로 — 끌 수가 없어서 구독 원장으로 옮겼다.
- 권한 인덱스에 캐시 — 스테일이 곧 누출.
- 자동완성 빈 질의를 서버 전량 조회로 — 그게 다시 규모 상한이 된다.
- 휴지통 우회 조회를 여러 곳에 흩는 것 — 네이티브 쿼리 한 곳으로 유지.
