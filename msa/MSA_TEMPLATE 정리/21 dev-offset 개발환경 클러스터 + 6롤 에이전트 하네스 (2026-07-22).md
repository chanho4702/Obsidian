# 21 — dev-offset 개발환경 클러스터 + 6롤 에이전트 하네스 (2026-07-22)

상위: [[00 개요 — 전체 구조]] · 선행: [[13 백엔드 컨테이너화 + compose 통합 — CI-CD Wave 1 (2026-07-15)]] · 관련: [[dev-env-ide-split]]

## 한눈에 보기

작업 자체가 아니라 **작업하는 환경**을 정비한 두 갈래다.

1. **dev-offset 클러스터** — CI가 배포한 도커 풀스택을 끄지 않고, 그 옆에 개발용 백엔드 6개를 **포트 +10000**으로 나란히 띄운다. 인프라(Postgres·Keycloak·Redis)는 도커 것을 재사용. 원커맨드 `scripts/dev-up-local.ps1`.
2. **6롤 에이전트 하네스** — 기획·디자이너·프론트·백엔드·운영·리뷰 6개 롤을 에이전트와 스킬로 고정했다. 롤이 뒤섞여 생기던 드리프트(임의 판단·서비스 경계 불일치·사라지는 UI)를 막는 게 목적.

두 갈래는 무관해 보이지만 같은 문제를 푼다: **"직전 작업의 문맥이 다음 작업에 안 남는다."** 하나는 실행 환경에서, 하나는 작업 절차에서.

# 1부. dev-offset 클러스터

## 1. 문제 — 도커를 끄지 않고 개발하고 싶다

[[13 백엔드 컨테이너화 + compose 통합 — CI-CD Wave 1 (2026-07-15)|13번]]·[[cicd-pipeline-structure]] 이후, 로컬에는 CI가 자동 배포한 **도커 풀스택**이 상시 떠 있다. 이게 "현재 배포본"이다.

그런데 코드를 고치려면 그 서비스를 IDE에서 띄워야 한다. 지금까지는 도커 쪽을 내렸다. 문제:

- 도커를 내리면 **배포본 상태를 잃는다.** "지금 배포된 게 잘 도나?"를 확인할 수 없다.
- 다시 올릴 때 `.env` 드리프트로 의존 서비스가 재생성되는 사고가 있었다(원장 사건 5, `--no-deps`로 차단).
- 서비스 하나 고치자고 6개를 내렸다 올리는 비용.

## 2. 해법 — 포트 +10000으로 통째로 비켜서기

**모든 dev 서비스가 기본 포트에 10000을 더한다.** 규칙이 하나라 외울 게 없다.

| 서비스 | 도커(배포본) | dev(IDE) |
|---|---|---|
| gateway-server | 8000 | **18000** |
| eureka-server | 8761 | **18761** |
| auth-server | 9000 | **19000** |
| board-service | 9100 | **19100** |
| wiki-backend | 9110 | **19110** |
| org-service (platform-backend) | 9130 / gRPC 9131 | **19130 / gRPC 19131** |

구현은 각 리포의 `src/main/resources/application-dev.yml` 한 장씩:

```yaml
# gateway-server/application-dev.yml
server:
  port: 18000
spring:
  data:
    redis:
      database: 1        # 도커(db0)와 레이트리미터 키 분리
eureka:
  client:
    service-url:
      defaultZone: http://localhost:18761/eureka
platform:
  jwks-uri: http://localhost:19000/.well-known/jwks.json
```

**설계 포인트 네 가지.**

**① 라우트는 하드코딩하지 않는다.** 게이트웨이 라우트가 `lb://`(Eureka 디스커버리)라, dev Eureka(:18761)에 dev 서비스들이 등록되면 **자동으로 연결된다**([[09 유레카 서비스 디스커버리 (2026-07-05)]]). dev용 uri를 따로 안 쓴다.

**② Redis는 포트가 아니라 논리 DB로 가른다.** 인프라는 도커 것을 공유하므로 Redis도 같은 :6379다. 대신 dev는 `database: 1`을 쓴다. 이걸 안 하면 게이트웨이 레이트리미터 키가 섞이고, wiki-backend의 **이벤트 스트림·컨슈머그룹이 도커와 dev 사이에 섞인다**([[17 Wave B — wiki-backend 구현기록, 과정과 원리 해설 (2026-07-21)|17번]]의 `platform:events:v1`).

**③ issuer/audience는 오버라이드하지 않는다.** `http://localhost:9000` / `platform-api`는 **문자열 계약**이지 네트워크 주소가 아니다([[keycloak-split-horizon-oidc]]에서 비싸게 배운 것). dev 클러스터 전체가 기본값을 공유해야 토큰이 서로 통한다. 여기서 "dev니까 :19000으로 바꾸자"고 하면 전 서비스의 JWT 검증이 깨진다.

**④ 호스트 포트 충돌은 사실상 하나뿐이었다.** 도커 compose가 백엔드 컨테이너 포트(9000·9100·9110·9130·8761)를 **호스트에 공개하지 않기** 때문이다(nginx·게이트웨이만 노출). 유일한 충돌인 gateway를 dev가 :18000으로 비켜서면서 공존이 성립한다.

## 3. 기동 — IntelliJ Run Config + 원커맨드 스크립트

[[dev-env-ide-split]]의 원칙(백엔드는 IntelliJ, 프론트는 VSCode+wt 탭)을 그대로 따른다.

각 백엔드 리포에 `.run/bootRun (dev).run.xml`을 뒀다. 하는 일은 환경변수 하나:

```xml
<option name="env">
  <map><entry key="SPRING_PROFILES_ACTIVE" value="dev" /></map>
</option>
```

실행 버튼 드롭다운에서 `bootRun` / `bootRun (dev)`를 고르는 것만으로 배포 프로필과 개발 프로필이 갈린다. 기동 순서는 자유다(Eureka가 재시도 등록). 관례는 eureka → auth → board → org → wiki → gateway.

나머지는 `scripts/dev-up-local.ps1`가 한다:

1. Docker Desktop 확인 → `infra/keycloak` compose up (postgres·keycloak·redis)
2. **Keycloak realm에 dev redirect URI 반영** (아래 §4)
3. 프론트 3개를 Windows Terminal 탭으로 오픈 — myFront는 `--mode devlocal`(`.env.devlocal`의 `VITE_API_BASE=:18000`), wiki/alm은 기본 dev 서버
4. 백엔드 6개는 **안내만 출력** — IntelliJ에서 사람이 누른다

> [!note] 스크립트가 백엔드를 안 띄우는 이유
> 띄울 수는 있다. 안 하는 건 **디버거를 붙일 수 없기 때문**이다. 개발용 클러스터의 목적은 브레이크포인트를 찍는 것이고, 그건 IDE가 프로세스를 소유해야 한다. 스크립트는 "사람이 못 하는 것"(인프라·realm 동기화·탭 배치)만 한다.

## 4. Keycloak redirect URI — 소스와 실행 중 컨테이너를 둘 다 고쳐야 한다

dev 게이트웨이(:18000)로 로그인하려면 Keycloak이 그 redirect URI를 **알고 있어야** 한다. 모르면 `Invalid parameter: redirect_uri`로 거부된다 — [[12 크로스앱 내비게이션 + redirect_uri 사건 + 운영 전환 로드맵 (2026-07-15)|12번]]에서 이미 한 번 크게 겪은 실패다.

여기엔 함정이 하나 있다. **`realm-export.json`을 고치는 것만으로는 아무 일도 안 일어난다.** 그건 *다음 fresh import*용 소스일 뿐, 이미 떠 있는 컨테이너의 DB에는 반영되지 않는다([[keycloak-jwt-platform-build]]의 "stale realm" 원인과 동일).

그래서 **양쪽을 다** 고친다:

- `infra/keycloak/realm-export.json` — 소스. `:18000`·`:19000`을 redirectUris·webOrigins·post.logout.redirect.uris에 추가.
- `infra/keycloak/sync-dev-redirects.sh` — 실행 중인 `platform-keycloak` 컨테이너에 `kcadm.sh`로 **즉시 반영**. 배열 전체를 원하는 최종값으로 `set` 하므로 **멱등** — 몇 번 재실행해도 안전하다.

```bash
docker exec "$KC" "$KCADM" update clients/"$CID" -r "$REALM" \
  -s 'redirectUris=[... , "http://localhost:18000/login/oauth2/code/keycloak", ...]' \
  -s 'webOrigins=[... , "http://localhost:18000", ...]' \
  -s 'attributes."post.logout.redirect.uris"="...##http://localhost:18000/*##..."'
```

> [!warning] Git Bash에서 docker exec가 깨지는 함정
> 스크립트 상단의 두 줄이 없으면 이 스크립트는 Windows에서 동작하지 않는다.
> ```bash
> export MSYS_NO_PATHCONV=1
> export MSYS2_ARG_CONV_EXCL='*'
> ```
> MSYS(Git Bash)는 `/opt/keycloak/bin/kcadm.sh` 같은 **컨테이너 내부 절대경로**를 호스트 Windows 경로로 자동 변환한다. 그래서 `docker exec`에 `C:/Program Files/Git/opt/keycloak/...`가 넘어가 "파일 없음"으로 죽는다. `http://...`와 `/*` 같은 인자도 같은 이유로 망가진다.

## 5. 남은 것

- **이 세 파일이 아직 우산 repo에 커밋되지 않았다** — `scripts/dev-up-local.ps1`, `infra/keycloak/sync-dev-redirects.sh`, 그리고 `realm-export.json` 수정분(변경만 있고 커밋 없음). 다음 인프라 커밋에 함께 넣을 것.
- `platform-backend`는 멀티모듈이라 `.run/`이 **`org-service/` 하위**에 있다(다른 리포는 루트). IntelliJ에서 열 때 혼동 주의.
- 종료 절차는 여전히 수동: 인프라는 `dev-down.ps1`, 프론트는 탭 닫기, 백엔드는 IntelliJ 정지 버튼.

# 2부. 6롤 에이전트 하네스

## 1. 문제 — 롤이 섞이면 드리프트가 난다

작업을 한 덩어리로 맡기면 세 가지가 반복해서 났다.

- **임의 판단** — 정책 결정이 필요한 지점에서 묻지 않고 스스로 정하고 지나간다.
- **서비스 경계 불일치** — 프론트 어댑터와 백엔드 응답 shape이 어긋난 채 양쪽 다 "완료"로 보고된다.
- **사라지는 UI** — 리팩터링 중 화면 요소가 조용히 없어지고, 테스트는 통과한다.

세 가지 다 **"누가 그걸 볼 책임인가"가 정해져 있지 않아서** 생긴다. 만드는 사람이 동시에 검사하면 자기가 만든 전제를 의심하지 않는다.

## 2. 구조 — 롤 ↔ 에이전트 ↔ 스킬

루트 `CLAUDE.md`에 하네스 절을 두고, 실체는 `.claude/agents/`(6개)와 `.claude/skills/`(플랫폼 8개)에 둔다.

| 롤 | 에이전트 | 주 스킬 |
|---|---|---|
| 기획 | `planner` | `product-planning` |
| 디자이너 | `designer` | `product-design` |
| 프론트엔드 | `frontend-engineer` | `platform-frontend` + `platform-integration` |
| 백엔드 | `backend-engineer` | `platform-backend` + `platform-integration` |
| 운영 | `ops-engineer` | `platform-ops` + `platform-integration` |
| 리뷰 | `reviewer` | `code-review` + `platform-integration` |

여기에 조율자 `platform-orchestrator` 스킬이 얹힌다.

**에이전트와 스킬을 나눈 이유.** 에이전트는 *누구인가*(역할·권한·판단 기준), 스킬은 *어떻게 하는가*(규약·체크리스트·함정)다. 둘을 합치면 규약을 고칠 때마다 에이전트를 건드려야 하고, 규약이 롤 사이에 공유되지 않는다. 실제로 `platform-integration`(경계면 규약)은 **네 롤이 함께 쓴다** — 분리했기 때문에 가능하다.

## 3. 파이프라인과 롤 선택

```
[기획] 스펙·태스크 분해
   ↓ 스펙 파일
[디자이너] 구성 명세 · 충실복제 · 접근성 · DS 확장안
   ↓ 구성 명세
[프론트 | 백엔드 | 운영]   ← 해당되는 롤만, 경계는 서로 조율
   ↓ 구현 diff + 통과 테스트
[리뷰] 경계면 교차비교 + 이중판정(스펙·품질) — 모듈 완성 직후 점진적으로
   ↺ Critical/Important → 해당 엔지니어 수정 → 재리뷰
```

전원 소집이 기본이 아니다. **요청 성격에 맞는 롤만**(2~5명):

- "화면 리뉴얼/디자인 재검토" → 기획(경량) · **디자이너(중점)** · 프론트 · 리뷰
- "백엔드 붙여/계약 변경" → 기획 · 백엔드 · 프론트(어댑터) · 리뷰
- "CI/배포/포트" → 운영 · 리뷰 (+영향 서비스 엔지니어)

한 롤·한 리포에 닫히는 작업은 **팀을 띄우지 않고** 해당 롤 스킬을 직접 쓴다. 단순 단일 파일 질문은 직접 응답.

## 4. 리뷰 롤이 이 하네스의 중심

`reviewer`가 다른 롤과 다른 점은 **"존재 확인이 아니라 교차 비교"**를 한다는 것이다.

> 백엔드 API 응답 shape과 프론트 store 어댑터를 **동시에 읽고** 대조한다 — id `Long`↔`string`, `content`↔`body`, 누락 필드로 인한 화면 깨짐, 장애 전파 누락(503→빈 목록 삼킴), base경로/포트/프록시 불일치.

[[20 프론트-백엔드 듀얼모드 연동 — 경계 매퍼·낙관적 락·503 전파 (2026-07-22)|20번]]의 "503을 빈 배열로 삼키던" 버그가 정확히 이 렌즈로 잡힌 종류다. "함수가 있다"로는 절대 안 잡힌다.

나머지 규칙:

- **이중 판정** — ① 스펙 준수(과·미달 구현) ② 코드 품질(YAGNI·테스트 위생·가독성). 하나만 통과하면 승인 아님.
- **점진적 QA** — 전체 완성 후 1회가 아니라 모듈 완성 직후.
- **반증적 검증** — "이게 진짜 버그인가"를 재현으로 확인. 심각도는 Critical / Important / Minor.
- **테스트를 약화시켜 통과시키라는 지시를 하지 않는다.**
- `general-purpose` 타입으로 동작한다 — 검증 스크립트·테스트를 **실제로 돌려야** 하므로 읽기전용 에이전트로는 안 된다.

## 5. 드리프트를 막는 나머지 장치

- **파일 기반 핸드오프** — 스펙은 `docs/superpowers/specs/`, 중간물은 대상 리포 `_workspace/`. 서브에이전트에는 diff를 붙여넣지 않고 **경로로** 넘긴다(컨텍스트 절약 + 산출물이 남음).
- **임의 기각 금지** — 스펙이 요구하는데 리뷰 기준상 결함이거나(plan-mandated) 서로 상충하면 **사용자 결정**을 받는다. 상충 데이터는 지우지 않고 출처를 병기한다.
- **누락은 무음이 아니다** — 재시도 후에도 실패하면 결과 없이 진행하되 보고서에 **명시**한다.
- **되돌리기 어려운 작업**(커밋/푸시·배포·마이그레이션)은 사용자 승인 후. main이면 브랜치 먼저.

## 6. 구성 직후 품질 게이트를 한 번 돌렸다

하네스를 만든 당일, 하네스 자신을 검수했다. 잡힌 것:

| 문제 | 조치 |
|---|---|
| `product-design`이 이관 전 이름 `wiki-frontend` 스킬을 참조(깨진 링크) | `platform-frontend` §3으로 정정 |
| `platform-integration`의 게이트웨이 포트 방향 오기 | `:18000` = dev 오프셋임을 명시 |
| 핸드오프 데이터 계약이 암묵적 | 기획→디자이너는 **캡처 인용**, 디자이너→프론트는 **구성 명세 §6**으로 명문화 |
| 스킬 트리거가 서로 겹침 | 경계 문구 추가 — `product-design`↔`platform-frontend`(결정 vs 구현), `code-review`↔`platform-integration`(판정 절차 vs 규약 지식), `orchestrator`↔개별 롤(2롤 이상 vs 단일 롤) |

같은 날 `wiki-front` 로컬의 `wiki-frontend` 스킬을 **`platform-frontend`로 일반화·이관**했다 — 세 프론트(wiki/alm/myFront)가 공유하는 규약이었기 때문이다.
