# 🎯 내 목표 — MSA Starter Template

> [!abstract] 한 문장
> **새 서비스 하나를 추가하면 인증·게이트웨이·관측·배포가 자동으로 붙는, 확장 가능한 MSA 스타터 템플릿**을 직접 만들고 그 위에 실제 **ALM/Wiki 플랫폼**을 올린다.
> 성장 경로: **Docker Compose → Kubernetes + ArgoCD → Spring AI**

표준화된 환경에서 빠르게 시작하고, 공통 모듈을 재사용하며, 인프라를 자유롭게 교체·확장할 수 있는 MSA 스타터 템플릿. 로컬 개발(Compose)부터 운영 배포(K8s), AI 확장까지 단계적으로 성장하도록 설계한다.

> [!success] 실제 구현 현황 (2026-08-15)
> 아래 로드맵(계획)과 별개로, 주력 제품은 **PMS → ALM/Wiki 플랫폼**으로 구체화됐다. 인증·게이트웨이·nginx 3앱 통합배포·GitHub Actions→GHCR·Alloy→Loki 관측이 서 있고, **Wave A**(org-service)·**Wave B**(wiki-backend)·**Wave C**(search-service)가 완료됐다. Wave C는 OpenSearch(Nori), Redis Streams 첫 소비자, 권한 필터 GraphQL, 관리자 재색인, 15컨테이너 풀스택과 자동배포까지 실측했다. 최신 기록은 [[00 개요 — 전체 구조]]와 [[25 Wave C — search-service 구현·배포 완료기록 (2026-08-15)]]. 이벤트 버스는 **Kafka가 아닌 Redis Streams**가 현행 확정 결정이다.

## 🏗️ 아키텍처 개요

요청 흐름:

```
Client → Nginx(:80) → Gateway(:8000) → auth / board / org / wiki / search
          3-SPA 단일 오리진       JWT 1차 차단       각 리소스 서버도 JWT 자체 검증

auth-server → Keycloak(OIDC + Google) → 자체 RS256 JWT/JWKS
wiki → Redis Streams → search → OpenSearch
wiki/search → org gRPC(권한), search → wiki gRPC(색인 조달)
```

로그인은 **Keycloak 리다이렉트 OIDC**, 프론트 토큰 계약은 **auth-server 자체 RS256 JWT**다. Gateway가 조기 차단하고 각 리소스 서버도 JWKS로 다시 검증한다. 현재 상세 토폴로지는 [[00 개요 — 전체 구조]].

## 🧩 핵심 구성 요소

### Gateway & 인증
| 구성 | 역할 |
|---|---|
| **Nginx** | Reverse Proxy, Static Files, SSL Termination |
| **API Gateway** (Spring Cloud Gateway) | Routing, Filter, Rate Limiting, Circuit Breaker, Logging |
| **auth-server** | Keycloak OIDC 위임, 자체 RS256 JWT·JWKS·`/api/me`·백채널 로그아웃 |
| **Keycloak** | OAuth2 / OIDC, Google SSO, 인증 세션 |
| **Eureka** | dev·auth/board 등록. Docker의 org/wiki/search는 Compose DNS 직결 |

### 공통 계약·모듈
| 모듈 | 역할 |
|---|---|
| `common-proto` (현행) | org·wiki gRPC 계약 + Redis Streams 이벤트 스키마, GitHub Packages 발행 |
| `starter-core` (계획) | 공통 응답·예외 표준화 |
| `starter-security` (계획) | JWT 검증·인가 경계 재사용 |
| `starter-logging` (계획) | stdout JSON·MDC·requestId 표준화 |

> 공통 응답·예외 표준화의 실제 구현 레퍼런스 → [[arms-engine-재사용패턴]]

### 인프라 (Infrastructure)
- **Data** — PostgreSQL 통일(서비스별 논리 DB) · Redis(rate limit + Streams) · OpenSearch 2.x + Nori(검색)
- **Identity** — Keycloak 26 + Google IdP
- **Secret** *(후속)* — 현재 `.env`·GitHub Secrets, 향후 HashiCorp Vault 이관
- **Discovery** — Eureka + Compose DNS 하이브리드. K8s 전환 시 CoreDNS/서비스 디스커버리로 수렴

### 관측 & 모니터링 (Observability)
- **현행 로그** — 앱 stdout JSON → Alloy → Loki → Grafana
- **후속** — Prometheus·Alertmanager·OpenTelemetry/Tempo, 전 서비스 requestId 상관관계

### DevOps & CI/CD
```
GitHub Actions 빌드/테스트 → GHCR latest + sha-* → repository_dispatch
  → self-hosted runner → docker compose pull/up --no-deps → healthy 대기·스모크
```
- 프론트 3개는 빌드한 `dist`를 배포 폴더에 교체하고 nginx가 서빙
- **후속** — SonarCloud 품질 게이트, ArgoCD GitOps ([[phase5-week-breakdown|Phase 5]])
- 상세 → [[phase1.5-cicd]]

## 🪜 두 가지 원칙

1. **이론은 just-in-time.** 책을 다 떼고 시작하지 말고, 템플릿에 실제 도메인을 붙여 문제를 만났을 때 그 주제를 판다. (느린 쿼리 → 그때 인덱스/실행계획)
2. **각 주는 DoD(완료 기준)로 끝낸다.** "읽었다"가 아니라 "돌아간다"로 판정. DoD 미통과 시 다음 주로 넘어가지 않는다.

## 🧱 템플릿 위에 올릴 것 — ALM/Wiki (구 PMS)

이 템플릿은 그 자체가 목적이 아니라 **플랫폼**이다. 그 위에 올릴 첫 제품은 원래 PMS로 잡았으나, **ALM + Wiki 플랫폼**(org-service·wiki-backend·alm 등으로 서비스 분할)으로 구체화됐다 → [[15 ALM·Wiki 백엔드 요구사항 + 서비스 분할 설계 (2026-07-19)]].
- 원래 순서는 "템플릿(플랫폼) 먼저 → 제품 나중"이었으나, 실제로는 **템플릿 완성 전에 ALM/Wiki 백엔드를 Wave A/B로 먼저 착수**해 병행 중이다.
- 템플릿엔 인증 뼈대(Keycloak Realm/Client/Role + Gateway JWT 검증)와 RBAC "꽂히는 자리"를 두고, 실제 권한 모델은 각 서비스(org-service의 권한 gRPC 등)에서 구현 → [[pms-backlog]]
- 현재: **Wave C 완료**(search-service/OpenSearch, proto v0.5.0) · 다음은 wiki-front 검색 UI 또는 Wave D(ALM 색인)
